# 화면 구성, 내비게이션과 사용 가이드

기준일: 2026-09-12. 이 문서는 공통 화면과 이동의 계약이다. 계정 권한·작업 상태·발행 승인의 판단은 각 소유 도메인에 남긴다. 화면·문서 추가가 실제 AI 실행이나 배포 완료를 뜻하지 않으며, 현재 검증 범위는 [검증 기록](../operations/verification.md)을 따른다.

## 1. 목적과 책임

비개발 매니저가 작업을 시작하고, 현재 위치를 파악하고, 요청·결과를 다시 찾을 수 있게 한다. 내부 CLI·모델·샌드박스·DB 개념은 메뉴로 나열하지 않는다.

- 소유: 헤더 메뉴의 이름·순서·표시, 현재 메뉴, 화면 경로, 공통 레이아웃, 매니저용 사용 가이드.
- 위임: 로그인·역할·객체 접근은 [계정](../accounts/README.md), 업무 데이터와 동작은 해당 도메인, 설치·기동은 [운영](../operations/README.md).
- 제품의 `Docs`는 서비스 사용 안내이며 저장소의 개발 기획 문서 `docs/`와 구별한다. 개발 문서·로컬 파일을 읽어 웹에 노출하는 문서 서버는 만들지 않는다.
- Project 빈 화면은 중앙 정렬하며 관리자는 짧은 설명·프로젝트 추가·등록 가이드, 매니저는 할당 안내·사용 가이드만 본다. 프로젝트가 있으면 본문의 추가 버튼 대신 관리자에게만 목록 네비 우측에 작은 `Add`를 표시한다. 헤더에는 추가하지 않는다. 상세 계약은 [프로젝트 기획](../projects/README.md#첫-사용-안내와-등록-화면)을 따른다.
- Docs의 기본 6개 매니저 안내는 유지하고, ADMIN에게만 `7. 관리자: 프로젝트 등록과 준비` 목차·본문을 추가한다. 등록 폼과 메인에서 `/docs/#project-setup`으로 연결한다.

## 2. 헤더 메뉴와 접근 범위

로그인 사용자에게 다음 순서로 표시한다. `AI`·`Admin`을 제외해도 나머지 순서는 유지한다.

| 순서 | 표시 | URL | MANAGER | ADMIN | 목적 |
| --- | --- | --- | --- | --- | --- |
| 1 | `Project` | `/projects/` | 표시 | 표시 | 프로젝트 선택·문제 상담 시작 |
| 2 | `Request` | `/requests/` | 표시 | 표시 | 접근 가능한 요청·실행·결과 찾기 |
| 3 | `AI` | `/ai/` | 숨김·접근 거부 | 표시 | 호스트 Codex 연결·모델·실행 준비 설정 |
| 4 | `Admin` | `/admin/` | 숨김·접근 거부 | 표시 | 요청 승인·계정 관리·운영 상태의 허브 |
| 5 | 문서 아이콘 (`Docs`) | `/docs/` | 표시 | 표시 | 한국어 매니저 사용 가이드 |
| 6 | 설정 아이콘 (`Account`) | `/accounts/me/` | 표시 | 표시 | 본인 아이디 확인, 닉네임·비밀번호 변경, 로그아웃 |

아이콘 링크에는 `Docs`, `Account`라는 접근 가능한 이름과 툴팁을 제공한다. 아이콘 자체는 중복 낭독하지 않으며 키보드로 이동·실행할 수 있다. 텍스트·아이콘 모두 현재 메뉴에 `aria-current="page"`를 적용하고 시각적으로 구별한다. 텍스트 메뉴는 굵게 표시한다.

로고는 `Project`로 연결하고 메인 `/`도 프로젝트 목록으로 보낸다. 익명 사용자는 로그인 화면으로 이동하며 업무 메뉴·객체 이름을 노출하지 않는다. 초기 비밀번호 변경 필요 등 기존 계정 조건은 `Docs`와 새 허브에도 동일하게 적용한다. 메뉴 숨김은 서버 접근 검사를 대신하지 않는다.

헤더에 로그아웃 버튼을 두지 않는다. `Account` 본문 맨 아래에 작은 버튼으로 제공하고, 기존 POST·CSRF·세션 폐기 계약을 보존한다.

## 3. Admin 허브와 활성 메뉴

`/admin/`은 제품의 관리자 전용 SSR 페이지이며 Django Admin 사이트가 아니다. 기존 화면을 모으는 링크 허브로, 새 승인 모델·업무 DB·권한 체계를 만들지 않는다.

| Admin 진입점 | 기존 화면 | 네비게이션 | 책임 |
| --- | --- | --- | --- |
| `요청 승인` | `/approvals/` | `Admin / Approvals` | 사용자 확인된 로컬 결과 승인·보완 요청, 별도의 원격 발행 검토 |
| `계정 관리` | `/accounts/manage/` | `Admin / Users` | 계정 생성·역할·활성 상태·프로젝트 할당 |
| `운영 상태` | `/operations/` | `Admin / Operations` | 저장된 worker·실행 준비·운영 상태 조회 |

`요청 승인`은 사용자 확인을 마친 [로컬 결과](../artifacts/README.md)와 별도로 준비된 [원격 발행](../approvals/README.md)의 진입점이다. 요청자의 명세 확인이나 로컬 수정 시작에 관리자 승인을 요구하지 않는다. 매니저는 결과에서 `작업 완료 · 관리자에게 전달` 또는 `재수정 요청`을 선택한다. 관리자는 승인 목록에서 결과를 열고 `로컬 결과 승인` 또는 `보완 요청`을 선택한다. 로컬 승인은 push·PR을 실행하지 않는다. 원격 발행은 승인된 결과 화면의 `관리자 발행 검토 준비` 이후 별도로 승인한다. 매니저에게 관리자 승인·push·PR 버튼을 제공하지 않으며 자기 결과의 발행 상태 조회는 유지한다.

| 현재 화면 계열 | 활성 헤더 메뉴 |
| --- | --- |
| 프로젝트 목록·상세·추가·설정·의존성·대화·프로젝트 발행 설정 | `Project` |
| 요청·실행·결과, 매니저의 발행 상태 조회 | `Request` |
| Codex 연결·모델·보호 점검 | `AI` |
| Admin 허브·계정 관리·운영 상태·관리자의 발행 검토/준비 | `Admin` |
| 서비스 사용 가이드 | `Docs` |
| 내 계정·비밀번호 변경 | `Account` |

`AI`는 Admin 하위로 합치지 않는다. 프로젝트별 발행 정책은 해당 프로젝트 설정이므로 `Project`를 유지한다. 같은 발행 상태 URL도 관리자 운영과 매니저의 자기 요청 조회 맥락을 구별하며 서버의 객체 권한은 바꾸지 않는다.

## 4. Navigation 경로 규칙

네비게이션은 헤더 바로 아래에서 현재 위치를 설명한다. 파일 트리처럼 `/`로 나누되 실제 파일 경로가 아니라 사용자가 아는 화면·프로젝트·요청 이름을 쓴다. 고정 화면 이름은 영문으로 통일하고 프로젝트·대화·요청의 사용자 입력 이름은 그대로 표시한다.

- `Project / 프로젝트 이름 / Conversations / 대화 제목`
- `Project / 프로젝트 이름 / Configuration`
- `Request / 요청 제목 / 실행 상태 / 변경 결과`
- `Admin / Approvals / Review Publication`
- `Account / Password`

상위 경로와 현재 페이지는 해당하는 안전한 GET 화면 링크로 제공하고, 마지막 항목에 `aria-current="page"`를 붙인다. 루트 페이지도 네비게이션을 표시한다. 폼 오류로 POST 응답을 렌더링해도 수정·승인·삭제 같은 동작 URL을 경로 링크로 만들지 않고 원래 GET 화면으로 연결한다.

경로에 넣는 객체 이름은 이미 접근 검사를 통과한 뷰 문맥만 사용한다. URL의 ID로 별도 조회해 권한 없는 프로젝트·요청 이름을 알아내지 않는다. 권한 오류·존재하지 않는 대상은 안전한 상위 화면과 비링크 `요청 확인` 등으로 안내한다. 이름은 이스케이프하며, UUID·저장소 절대 경로를 화면 이름 대신 사용하지 않는다. 네비는 버튼 유무와 화면 폭에 관계없이 경계선을 포함해 48px로 고정한다. 긴 경로는 한 줄을 유지하고 경로 영역 안에서 가로 스크롤하며, 우측 Add는 스크롤되지 않는다. 키보드로 경로 링크를 탐색할 수 있어야 한다.

## 5. 매니저용 Docs

`GET /docs/`는 로그인 사용자가 읽는 한국어 가이드다. 다른 사용자·프로젝트·작업 데이터나 개발 기획 파일을 조회하지 않는 정적 SSR 화면이다. 아래 흐름을 실제 화면의 버튼 이름으로 설명하고 페이지 내부 목차로 필요한 부분에 이동하게 한다.

| 가이드 항목 | 안내할 내용 |
| --- | --- |
| 시작·계정 | 관리자에게 계정을 받아 로그인, 필요한 초기 비밀번호 변경, 할당 프로젝트가 없으면 관리자에게 문의 |
| 메뉴·현재 위치 | `Project`, `Request`, `Docs`, `Account` 역할, 경로 링크로 상위 화면 이동, `AI`·`Admin`은 관리자 전용 |
| 질문·문제 설명 | `Project` → 프로젝트 → `문제 상담·내 요청` → 설명 입력 → `대화 시작`, 후속 `설명 보내기` |
| 요청·명세 확인 | `요청으로 정리`, `초안 저장`, 선택적 `저장한 내용으로 AI 제안 받기`·`이 제안을 초안에 반영`, `이 명세로 준비`와 `수정 작업 시작`의 구분 |
| 진행·취소·재시도 | `Request`에서 실행 다시 찾기, `취소 요청`, 종료 뒤 `새 실행으로 재시도`; 기존 실행에 새 설명이 자동 적용되지 않음 |
| 결과·관리자 검토 | `결과 확인`에서 변경·검증 증거·패치를 읽고 `재수정 요청` 또는 `작업 완료 · 관리자에게 전달` 선택, 관리자 로컬 승인과 별도 원격 발행 구분 |
| 오류·자료 주의 | AI 사용 불가·준비 실패·보관·권한 오류는 안내를 읽고 관리자에게 문의, 비밀번호·토큰·개인정보 입력 금지, 코드·자료의 외부 모델 전송 안내 |
| 계정 마무리 | 설정 아이콘 `Account` → 아이디 확인, 닉네임 편집 후 `내 정보 저장`, `비밀번호 변경`, 페이지 맨 아래 `로그아웃` |

가이드는 사용할 수 있는 동작과 그 조건을 설명한다. AI 보호 검사 실패·worker 미기동·검증 미실행을 정상 완료로 안내하지 않는다. 실제 모델 호출 성공, 원격 push/PR, merge 또는 배포가 끝났다고 정적 가이드에서 보장하지 않는다. 프로젝트 등록·모델 설정·호스트 CLI 조작을 매니저의 필수 준비로 안내하지 않는다.

## 6. 레이아웃과 코드 배치

| 영역 | 의미와 DOM | 코드 소유 |
| --- | --- | --- |
| Header | 최상단 로고·역할별 메뉴, `<header class="site-header">` | `templates/includes/header.html` |
| Navigation | 현재 화면·경로, `<nav class="site-navigation" aria-label="현재 위치">` | `apps/navigation.py`, `templates/includes/navigation.html` |
| Notification | 메시지가 있을 때만 네비 바로 아래 표시, `<div class="site-notifications" role="status" aria-label="알림">` | `templates/includes/notifications.html` |
| Main | 페이지별 내용, `<main class="site-main container">` | `templates/base.html`의 content block과 도메인 템플릿 |
| Footer | 작은 저작권·GitHub/LinkedIn 링크, `<footer class="site-footer">` | `templates/includes/footer.html` |

`templates/base.html`은 위 영역을 순서대로 조합한다. 흰색 헤더와 밝은 회색 네비 배경을 구분하고 두 영역 사이의 큰 여백을 없앤다. 본문과 네비를 같은 헤더로 묶지 않는다. 푸터는 왼쪽 `© kimchanhyung98`, 오른쪽 GitHub·LinkedIn 아이콘이며 외부 프로필 링크를 유지한다. 공통 CSS는 `static/css/app.css`에 둔다.

공통 디자인은 흰 배경·중립색·얇은 구분선 중심이다. 모든 섹션을 큰 둥근 카드로 감싸지 않는다. 현재 페이지 이름과 상위 이동은 네비가 담당하므로 본문의 중복 제목·`돌아가기`·상위 목록 링크는 제거한다. 오류 안내·실행 상태·섹션 제목과 원래 대화·결과 확인 같은 업무 전환 링크는 유지한다.

모든 페이지에서 본문 최상위 제목은 표시하지 않는다. 실행 상태·오류·접수 결과는 큰 제목 대신 일반 안내 문구로 유지하며, Docs의 내용별 섹션 제목은 보존한다. 프로젝트 등록 네비는 `Project / Add Project`로 표시한다. 등록 폼은 입력란별 도움말을 사용하고, 하단 우측의 등록 버튼 왼쪽에 가이드 링크를 배치한다.

로그인 본문은 최대 360px 폭의 폼을 가로·세로 중앙에 배치한다. 중복 제목과 상시 안내 문구 없이 `아이디`·`비밀번호`·`로그인`만 표시하되, 입력 오류와 비밀번호 변경 후 알림은 유지한다. 공통 헤더·네비·푸터와 인증 동작은 바꾸지 않으며, 좁거나 낮은 화면에서는 자연스럽게 스크롤할 수 있어야 한다.

입력 폼은 최대 720px로 제한하고 `templates/includes/form_fields.html`로 필드·안내·오류를 공통 출력한다. 체크박스와 라벨은 같은 줄에서 시작하며 긴 라벨은 입력 옆에서 줄바꿈한다. 숨김 값·필수 입력·라벨 연결·오류·도움말 연결은 보존한다. 버튼은 데스크톱에서 34px 이상, 좁은 화면과 터치 입력 환경에서 44px 이상으로 배치하며 주 저장 동작과 보조 동작을 구분한다. 단순 조회·재점검·취소를 모두 강조 버튼으로 만들지 않는다. AI 모델 표는 모바일에서 모델별 2열 정보 묶음으로 배치하고, 나머지 넓은 표는 표 영역 안에서 스크롤한다. Admin의 관리 기능은 카드 그리드 대신 세로 목록으로 제공한다.

`apps/portal/`은 `/admin/`·`/docs/`의 인증·역할 검사와 정적 렌더링만 담당한다. 가이드는 `templates/portal/docs.html`, 관리 허브는 `templates/portal/admin.html`에 둔다. 업무 실행·승인·계정 변경은 기존 도메인으로 연결하고 이 허브에 복제하지 않는다.

공통 영역 순서는 `Header → Navigation → Notification(메시지가 있을 때만) → Main → Footer`다. 프로젝트 등록 완료 등 Django 메시지는 본문 안이 아닌 이 노티 영역에 한 번만 표시한다. 노티는 옅은 배경의 전체 폭 띠이며 내부 텍스트는 네비·본문과 같은 컨테이너에 정렬한다. 스크롤에 겹치는 오버레이가 아닌 문서 흐름의 고정된 위치이며, 메시지가 없으면 빈 영역을 hidden으로 숨겨 여백을 만들지 않는다. 입력란 검증 오류는 해당 폼에 남긴다.

노티 우측의 X 버튼(`알림 닫기`)은 해당 페이지의 알림 전체를 닫는다. 알림은 자동으로 사라지지 않으며 같은 페이지 새로고침에는 유지한다. 직접 닫거나 다른 페이지(경로 또는 쿼리 변경)로 이동하면 제거하고 뒤로 돌아와도 다시 표시하지 않는다. 앵커 이동은 같은 페이지로 취급한다. Django 메시지 소비는 그대로 유지하되 `static/js/notifications.js`가 현재 탭의 sessionStorage에 계정·페이지·텍스트만 저장해 복원한다. 새 서버 메시지가 있으면 기존 표시를 교체하고, 계정이 바뀌면 이전 알림은 제거한다. HTML로 복원하지 않는다. JavaScript 또는 브라우저 저장소를 사용할 수 없으면 최초 서버 메시지만 표시할 수 있으며 새로고침 유지 기능은 제공되지 않는다.

## 7. 결정과 수용 기준

### 페이지별 구성

- 대화 시작: 프로젝트 설명과 중복 제목 없이 입력 폼과 대화 이력을 분리한다. 1024px 이상은 입력·이력 2열, 이하에서는 세로로 배치한다. 입력 아래에 작성 방법·민감정보 주의, 하단 우측에 시작 버튼과 가이드 링크를 둔다.
- Request: 요청이 없으면 중앙에 짧은 역할별 안내·Project 이동·가이드를 표시한다. 요청이 있으면 제목·프로젝트·상태를 행 단위로 구분한다. 상세는 명세 보완·제안·확인·실행 이력을 섹션으로 구분한다.
- AI: 연결과 실행 보호의 확인 여부를 상단에 분리한다. 연결 확인은 현재 페이지 안에서 결과를 표시하며 GET에서 자동 점검하지 않는다. 모델 목록은 상시 표시하고 새 프로필 폼은 펼침 영역에 둔다. 마지막 보호 기록을 현재 실행 보장으로 표시하지 않는다.
- Admin: 요청 승인·계정 관리·운영 상태를 각각 한 줄 설명이 있는 이동 목록으로 제공한다. 계정 생성 폼은 펼쳐서 사용하며 이 화면에는 로그아웃을 두지 않는다.
- Account·Password: 최대 720px 폭 안에서 폼·작업 버튼·구분선을 정렬한다. 아이디는 읽기 전용, 닉네임만 편집하며 이메일을 표시하지 않는다. Account 하단의 로그아웃은 유지한다.
- 설정 폼은 입력 폭 안에서 주 제출 버튼을 우측 정렬한다. 긴 대화·명세·가이드는 최대 800px 읽기 폭을 사용하며, 결과 diff와 표는 넓은 본문 또는 내부 스크롤을 유지한다.
- Docs는 매니저 가이드이며 상세한 실행 원리·관리자 준비 설명을 업무 화면의 상시 문구 대신 제공한다. 관리자 AI 설정 안내는 `/docs/#ai-setup`으로 연결한다.

### 반응형 그리드

- 화면 전체를 채우는 대시보드가 아닌 중앙 정렬된 최대 너비 레이아웃을 사용한다. 헤더·네비·노티·푸터의 배경과 경계선만 화면 전체 폭으로 표시한다. 내부 콘텐츠와 본문은 동일한 `.container`를 사용하며 좌우 기준선이 일치해야 한다.
- 공통 컨테이너는 패딩을 포함해 최대 1140px이며 650px 이하에서 좌우 16px, 그보다 넓으면 24px 여백을 사용한다. `--layout-max-width`와 `--layout-gutter`로 공통 관리한다. 넓은 화면의 남는 공간은 좌우에 균등하게 둔다.
- Admin 이동 목록의 구분선과 화살표는 본문 전체 너비를 사용한다. 목록 자체에 별도의 800px 제한을 적용하지 않는다. 입력 폼(720px)과 긴 읽기 콘텐츠(800px)의 제한은 가독성을 위한 내부 영역이며 공통 컨테이너를 변경하지 않는다. 이 내부 영역은 본문 왼쪽 기준선에 맞추고 로그인·빈 상태만 중앙에 배치한다.
- 프로젝트 상세는 1024px 이상에서 본문 + 관리 영역 2열과 요약 4열, 1023px 이하에서 본문·관리 영역을 세로 배치하고 요약은 2열로 표시한다. 관리자가 아닌 사용자는 항상 본문 1열이다. 태블릿·모바일의 관리 링크는 2열로 배치한다.
- 650px 이하의 헤더는 로고와 메뉴를 두 줄로 구분한다. 1023px 이하 또는 터치 입력 환경에서는 주요 버튼, 메뉴, 관리 링크를 높이 44px 이상으로 제공한다. 넓은 태블릿 가로 화면에도 터치 규칙을 적용하며, 네비의 작은 Add는 기존 28px 높이를 유지한다.
- 긴 프로젝트 이름·브랜치·경로는 그리드 폭 안에서 줄바꿈하고, 표·코드는 해당 영역 내부 스크롤을 사용한다. 페이지 전체 가로 스크롤이나 영역 겹침은 허용하지 않는다.
- 회귀 검사는 320·390·600·768·820·1023·1024·1280·1920px에서 관리자·매니저 상세 화면을 확인한다. 320·820·1920px에서는 주요 공통 페이지와 합성 긴 문자열도 검사하며, 390·1024·1366px에서 터치 입력 환경을 확인한다. Chromium·Firefox·WebKit의 뷰포트·터치 에뮬레이션 검증이며 실제 휴대폰·태블릿 하드웨어 테스트와 구별한다.

### 중요한 작업의 제출 확인

- 동의·확인용 체크박스는 사용하지 않는다. 계정 활성화·모델 사용·발행 사용 및 자료 선택처럼 실제 설정을 나타내는 체크박스는 유지한다.
- 프로젝트 등록·설정·상태, 계정 생성·권한·할당·비밀번호 변경, 모델 프로필 저장·검증, 명세 확정·AI 제안 반영·수정 실행·취소·재시도, 발행 설정·준비·승인 작업은 공통 `예 / 아니오` 모달을 사용한다. 로그인·로그아웃·단순 조회·일반 초안 저장은 추가 확인 없이 동작한다.
- HTML 필수 입력·형식 검증을 통과한 뒤 모달을 열고 `아니오`에 초점을 둔다. 아니오·Esc는 전송하지 않고 입력과 원래 버튼 초점을 유지한다. 예는 원래 submit 버튼·formaction·멱등키·CSRF를 보존해 한 번 제출한다. 비밀번호와 숨김 인증값은 요약에 노출하지 않는다.
- 모달은 오조작 방지 UI이며 보안 경계나 서버 승인 기록을 대신하지 않는다. 서버의 형식·실제 저장소·권한·버전·멱등성·승인 검사는 유지한다. AI 최소 호출은 예를 누른 경우에만 기존 consent 값을 전송한다.
- 확인 스크립트가 준비되기 전에는 해당 폼을 inert 상태로 두며 JavaScript 미사용 시 활성화 안내를 제공한다. 공통 템플릿은 `templates/includes/confirmation.html`, 동작은 `static/js/confirmation.js`가 소유한다.

- NAV-01: Header·Navigation·Main·Footer를 별도 영역과 템플릿으로 구분한다.
- NAV-02: 헤더 순서는 Project / Request / AI / Admin / Docs / Account이며 AI·Admin은 ADMIN 전용이다.
- NAV-03: Docs는 문서 아이콘의 매니저 사용 가이드, Account는 설정 아이콘의 내 계정이다.
- NAV-04: Admin은 기존 승인·계정·운영 화면의 허브이며 새로운 명세·실행 승인 기능이 아니다.

아래는 수용 기준이며 체크 완료는 해당 검증 증거를 별도로 기록한 뒤 판단한다.

- [ ] NAV-AC-01: ADMIN·MANAGER 헤더의 순서·링크·아이콘 이름이 표와 같고 익명 사용자에게 업무 메뉴가 노출되지 않는다.
- [ ] NAV-AC-02: 관리자 전용 화면과 승인 동작은 매니저 직접 요청을 거부하되, 권한 있는 자기 결과의 발행 상태 읽기는 유지한다. Docs는 기존 로그인·초기 비밀번호 변경 조건을 유지한다.
- [ ] NAV-AC-03: 프로젝트·요청·실행·결과·계정·Admin 하위 화면에서 올바른 메뉴 하나가 활성이고 경로 링크는 안전한 GET 화면을 연다.
- [ ] NAV-AC-04: 권한 없는 객체 이름·ID·로컬 경로가 네비에 노출되지 않고 긴 이름·HTML 입력·POST 오류를 안전하게 표시한다.
- [ ] NAV-AC-05: 실제 브라우저에서 헤더·네비의 간격과 배경이 구분되고 키보드·좁은 화면에서 아이콘·경로·본문·푸터를 사용할 수 있다.
- [ ] NAV-AC-06: Docs는 실제 버튼명과 조건부 작업 흐름을 설명하고 개발 기획·비밀·타인 데이터를 노출하지 않으며 페이지 조회로 AI 호출·업무 변경이 발생하지 않는다.
