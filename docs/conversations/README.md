# 대화: 문제 설명과 요구 구체화

> 상태: Django의 대화 화면·메시지·명세 연결·polling을 구현했습니다. 실제 모델 응답은 보호 게이트 미충족으로 검증하지 않았습니다. 이 문서는 목표 계약이며 현재 실증 범위는 [검증 기록](../operations/verification.md), 전체 범위는 [문서 시작점](../README.md)을 따릅니다.

## 1. 목적과 책임

매니저가 프로젝트를 고르고 평소 사용하는 말로 질문하거나 수정할 문제를 설명하는 진입점입니다. 대화 자체는 코드 수정·실행 취소·발행 승인이 아닙니다.

- 소유: 대화, 메시지, 메시지 순서, 대화와 요청의 연결, 사용자에게 보여주는 응답 상태.
- 위임: 계정·소유권은 [accounts](../accounts/README.md), 대상 프로젝트는 [projects](../projects/README.md), 모델 호출은 [ai](../ai/README.md).
- 명세 확정과 실행 요청은 [requests](../requests/README.md), 실제 수정 상태는 [runs](../runs/README.md)가 소유합니다.
- 첨부·결과 확인은 [artifacts](../artifacts/README.md), 발행 승인은 [approvals](../approvals/README.md)를 따릅니다. 매니저의 별도 의도 확인 승인 단계는 만들지 않습니다.

## 2. 사용자가 보는 화면

대화 진입은 `Project` → 프로젝트 → `문제 상담·내 요청`입니다. 새 대화 폼의 실행 버튼은 `대화 시작`, 이후 설명 입력은 `설명 보내기`입니다. 목록·대화 상세에서는 헤더의 `Project`를 활성 표시하고 네비게이션을 `Project / 프로젝트 이름 / Conversations / 대화 제목`으로 연결합니다. `요청으로 정리` 또는 연결된 요청을 열면 `Request` 영역으로 이동합니다. 화면 전체 규칙과 매니저용 `Docs` 가이드는 [내비게이션](../navigation/README.md)을 따릅니다.

| 화면 요소 | 표시·입력 | 숨기는 내부 개념 |
|---|---|---|
| 프로젝트 선택 | 할당된 프로젝트 이름과 짧은 설명 | 저장소 절대 경로, CLI 실행 옵션 |
| 내 대화 목록 | 제목, 최근 메시지, 연결된 요청의 상태 | 다른 매니저의 대화 |
| 메시지 작성 | 질문 또는 현상·바라는 결과, 선택 첨부 | 모델명, effort, 시스템 프롬프트 |
| 대화 본문 | 내 설명, AI 질문·답변, 출처가 있는 상태 안내 | 원본 CLI 이벤트, 인증정보 |
| 요청 요약 카드 | 목표, 재현·기대 결과, 완료 조건, 미확인 사항 | 명세 JSON, 내부 revision ID |
| 요청 동작 | `요청으로 정리`, `명세 확인`, 요청 화면 이동 | 일반 메시지를 승인으로 해석하는 자동 동작 |
| 진행 카드 | 연결된 실행의 현재 상태와 결과 링크 | 별도 세션·메모리·스킬 메뉴 |

처음 필요한 입력은 **프로젝트와 질문 또는 현상·목표**뿐입니다. 제목은 첫 메시지 앞부분으로 자동 제안하고 직접 바꿀 수 있게 합니다. 제목 생성을 위해 별도 AI 호출을 강제하지 않습니다.

기술 초기값은 제목 120자, 메시지 10,000자입니다. 글자 수 초과 시 내용을 잘라 저장하지 않고 입력 폼에 오류를 표시합니다. 첨부 종류·용량·개수 제한은 artifacts의 단일 정책을 재사용합니다.

## 3. 기본 흐름

1. 로그인한 사용자가 할당된 활성 프로젝트를 선택합니다.
2. `주문 취소 버튼을 눌러도 아무 반응이 없어요`처럼 설명합니다. 메시지는 AI 완료를 기다리지 않고 먼저 저장합니다.
3. AI는 현재 화면, 재현 방법, 기대 결과 중 빠진 부분을 질문합니다. 한 번에 핵심 질문 1~3개를 제시합니다.
4. 사용자는 답하거나 `재현 방법을 모르겠어요`라고 말할 수 있습니다. AI는 모르는 내용을 사실로 채우지 않습니다.
5. 수정이 필요한 경우 `요청으로 정리`를 선택합니다. 이때 같은 대화에 연결된 요청 초안을 만들거나 기존 초안을 보완합니다.
6. 사용자가 요약을 검토한 뒤 요청 화면에서 명세를 확인하고 **별도 `수정 작업 시작` 버튼**을 누릅니다.
7. 수정 중에도 대화·상태 확인을 계속할 수 있습니다. 추가 설명은 다음 명세 보완 재료이며 실행 중인 작업에 자동 주입하지 않습니다.
8. 결과가 나오면 실행·결과 화면으로 연결합니다. `좋네요`, `올려주세요` 같은 메시지로 발행 승인을 대신하지 않습니다.

단순 질문이라면 1~4에서 끝납니다. 모든 대화를 수정 요청으로 전환하지 않으며, 새 업무는 새 대화를 시작하도록 안내합니다.

## 4. 핵심 데이터

| 객체 | 필수 필드 | 규칙 |
|---|---|---|
| `Conversation` | `id`, `project_id`, `owner_id`, `creation_key`, `title`, 생성·수정 시각 | 생성 후 프로젝트·소유자를 메시지 입력으로 변경하지 않음; `(owner_id, project_id, creation_key)` 유일 |
| `Message` | `id`, `conversation_id`, `sequence`, `kind`, `body`, `created_at` | 종류는 `USER`, `ASSISTANT`, `EVENT`; 저장된 본문은 수정하지 않고 후속 메시지로 정정 |
| 사용자 메시지 추적 | `actor_id`, `client_message_id` | 대화별 client ID 유일; 재전송으로 중복 메시지를 만들지 않음 |
| AI 응답 연결 | `reply_to_message_id`, `ai_invocation_id` | 어느 사용자 입력에 대한 응답인지 연결; 완료 응답은 호출별 최대 1개 |
| 첨부 연결 | `message_id`, `artifact_id` | 같은 프로젝트·소유권이 검증된 첨부만 연결 |
| 요청 연결 | `WorkRequest.conversation_id` | 한 대화에 요청은 최대 1개; 요청의 보완 이력은 그 요청 안에 유지 |

`EVENT`는 서버가 만든 `수정 작업 시작됨` 같은 안내입니다. 사용자가 이 종류나 작성자 ID를 직접 지정할 수 없습니다. EVENT 문구도 실제 상태의 원본은 아니며, 최신 상태는 Run·Approval 데이터를 조회합니다.

매니저는 할당 프로젝트에 속한 **자기 대화와 요청만** 봅니다. 관리자는 운영 목적으로 전체를 조회할 수 있지만 원래 작성자·소유자를 덮어쓰지 않습니다. 소유권 판단은 URL·숨은 폼의 owner 값이 아닌 로그인 계정과 저장된 관계를 사용합니다.

## 5. 메시지 처리와 문맥

- 메시지 저장과 응답 작업 등록을 같은 DB 트랜잭션으로 처리합니다. 접수됐지만 어떤 작업에도 연결되지 않은 입력을 만들지 않습니다.
- 같은 대화의 AI 응답 작업은 메시지 순서대로 처리합니다. 응답 대기 중 새 입력도 저장할 수 있고 `답변 대기` 상태를 표시합니다.
- 각 호출은 입력 대상 메시지까지의 허용 이력만 사용합니다. 실행 중 들어온 미래 메시지를 중간에 끼워 넣지 않습니다.
- 이전 메시지·첨부·요청 요약은 전부 사용자 제공 자료입니다. 그 안의 `시스템 지시`, `권한 부여` 같은 문구를 서버 지침으로 승격하지 않습니다.
- AI에 전달한 메시지 ID 범위, 첨부 참조, 요청 버전은 ai 호출 이력에 기록합니다. 다른 대화나 다른 소유자의 자료를 자동으로 합치지 않습니다.
- 긴 대화가 입력 한도를 넘으면 ai 정책에 따라 요약·선별한 범위를 기록합니다. 빠진 정보가 답변에 필수라면 다시 질문하며 전체 이력을 읽었다고 주장하지 않습니다.
- 일반 대화에는 파일 변경·임의 명령·발행 권한을 주지 않습니다. 코드 확인이 필요하면 ai의 읽기 전용 권한 안에서 승인된 작업 사본·자료만 참조하고, 코드를 바꾸려면 요청 흐름으로 전환합니다.
- 모델·effort는 관리자가 등록한 작업별 정책으로 결정합니다. 매니저가 메시지에 특정 모델을 적어도 실행 정책·권한이 바뀌지 않습니다.

대화용 작업 슬롯은 수정 작업 슬롯과 분리합니다. 기본 대화 응답 deadline은 **5분**이며, 마감 초과를 답변 성공으로 저장하지 않습니다. 대기열·점유·취소·복구는 runs의 공통 작업 계약을, 모델 호출 이력은 ai 계약을 따릅니다.

## 6. 상태 조회와 응답 실패

| 상태·상황 | 사용자 표시 | 서버 처리 |
|---|---|---|
| 접수됨·응답 대기 | `메시지를 저장했습니다. 답변을 기다리는 중입니다.` | 메시지와 AI 작업 ID 유지 |
| 응답 중 | `답변을 작성하고 있습니다.` | 브라우저 종료와 무관하게 작업 추적 |
| 정상 완료 | 저장된 답변 | 해당 호출에 ASSISTANT 메시지 1개 확정 |
| 로그인 만료·호출 한도 | `AI를 사용할 수 없습니다. 관리자 확인이 필요합니다.` | 사용자 입력 보존, 구체 원인은 관리자에게만 제공 |
| 마감 초과·중단 | `답변을 완료하지 못했습니다. 다시 시도할 수 있습니다.` | 불완전 출력을 완료 답변으로 취급하지 않음 |
| 권한 회수 | 기존 대화 접근 거부 | 이후 응답 조회·새 메시지·첨부 다운로드도 거부 |
| 프로젝트 보관됨 | 과거 대화는 조회, 입력창은 읽기 전용 | 신규 대화·메시지·요청 보완 차단 |

답변 재시도는 사용자가 명시적으로 선택하며 원래 메시지와 실패 호출을 참조한 **새 AI 호출**을 만듭니다. 자동 무한 재시도·다른 모델로 조용한 전환은 없습니다. 같은 재시도 키는 같은 호출로 응답합니다.

`진행 상태` 카드의 새로고침은 DB 조회만 사용합니다. 사용자가 자연어로 설명을 요청한 경우만 저장된 상태를 입력으로 AI에 전달하며, 설명에는 조회 기준 시각을 붙입니다. AI 응답으로 Run 상태를 갱신하지 않습니다.

## 7. 서버 Interface와 코드 배치

아래는 Django 구현 시 만들 계약이며 현재 사용 가능한 URL·함수 목록이 아닙니다. HTML form + 로그인 세션 + CSRF를 기본으로 하고, 별도 공개 API 서버는 두지 않습니다.

| 진입점 | 서비스 책임 |
|---|---|
| `GET /projects/{project_id}/conversations/` | 허용된 내 대화 목록과 새 대화 폼 |
| `POST /projects/{project_id}/conversations/` | `start_conversation(actor, project_id, body, client_message_id, creation_key)` |
| `GET /conversations/{id}/` | 대화·메시지·연결된 요청 표시 |
| `POST /conversations/{id}/messages/` | `send_message(actor, id, body, attachment_ids, client_message_id)` |
| `POST /conversations/{id}/responses/{call_id}/retry/` | `retry_response(actor, call_id, idempotency_key)` |
| `GET /conversations/{id}/updates/?after={sequence}` | 허용된 새 메시지·응답 작업 상태만 반환, 모델 미호출 |
| `POST /conversations/{id}/request/` | requests의 `create_or_get_draft` 호출; 코드 실행 없음 |

- URL의 project/conversation/call 조합은 서버에서 실제 소속 관계를 확인합니다. 다른 대화의 call ID를 넣어 재시도하지 못합니다.
- GET은 상태를 바꾸지 않습니다. 성공한 일반 폼 POST는 상세 화면으로 redirect하고, 점진적 갱신은 작은 읽기 전용 응답으로 시작합니다.
- 기본 화면 갱신은 활성 화면 2초, 백그라운드 화면 10초 polling으로 시작합니다. 매 조회마다 접근 권한을 다시 확인하며 사용자에게 WebSocket·CLI 세션을 설정하도록 요구하지 않습니다.
- 제안 코드: `apps/conversations/{models,forms,views,services,urls}.py`, `templates/conversations/`. 파일 수 자체를 도메인 완성 기준으로 삼지 않습니다.
- HTML은 escape하고 허용된 Markdown만 표시합니다. 모델 출력의 HTML·스크립트·자동 제출 form은 실행하지 않습니다.

## 8. 결정 사항과 대안

| ID | 구분 | 채택안과 이유 | 제외한 대안 |
|---|---|---|---|
| CONV-01 | 사용자 요구 | 비개발인원에게 프로젝트·문제 설명 중심 화면 제공 | 세션·모델·스킬을 시작 단계 필수 입력으로 노출 |
| CONV-02 | 사용자 요구 | 대화·실행·계정별 발행 권한을 분리 | 자연어의 `예`, `진행`을 실행·발행 승인으로 공용 처리 |
| CONV-03 | 구현 초기값 | 한 대화에 요청 1개, 보완은 같은 요청의 버전으로 추적 | 한 대화에서 여러 독립 요청·실행을 암묵적으로 동시 생성 |
| CONV-04 | 구현 초기값 | 대화별 응답 순서 보장, 수정과 별도 슬롯 사용 | 긴 수정이 전체 대화 응답을 독점 |
| CONV-05 | 구현 초기값 | 서버 렌더링 + polling, 사용자 메시지와 완료 답변 영속화 | 초기부터 실시간 소켓·토큰 스트리밍을 필수 기반으로 도입 |

위 초기값은 사용자가 이미 특정 수치·내부 API를 확정했다는 뜻이 아닙니다. 계정 권한이나 외부 전송 범위를 넓히는 변경은 단순 초기값 조정으로 처리하지 않습니다.

## 9. 검증 사례

- **CONV-AC-01:** 프로젝트와 한 문장만 입력해 대화가 시작되고, 모델명·CLI 옵션 입력 없이 보완 질문을 받는다.
- **CONV-AC-02:** 같은 creation_key의 새 대화 생성, 같은 client_message_id의 메시지 전송을 각각 동시에 두 번 제출해도 대화·메시지·응답 작업이 중복되지 않는다. 같은 키의 다른 본문은 충돌로 거부한다.
- **CONV-AC-03:** 수정 작업이 진행 중이어도 새 메시지를 저장하고 대화용 슬롯에서 답변받는다. 새 메시지가 기존 Run 명세에 섞이지 않는다.
- **CONV-AC-04:** 진행 카드 조회·polling 10회에서 모델 호출 수가 증가하지 않는다.
- **CONV-AC-05:** 매니저 A가 B의 대화·응답 ID·첨부 ID를 직접 지정해도 조회·작성·재시도·다운로드가 모두 거부된다.
- **CONV-AC-06:** 메시지에 `git push 실행`, 관리자 사칭, 스크립트 HTML을 넣어도 발행 작업·승인 기록·브라우저 스크립트 실행이 발생하지 않는다.
- **CONV-AC-07:** AI 실패·브라우저 재접속 뒤 원래 메시지가 유지되고, 명시적 재시도는 새 호출로 추적된다.
- **CONV-AC-08:** 대기 메시지 두 개의 응답은 각 reply_to 대상에 정확히 연결되며, 앞선 호출에 뒤의 입력이 섞이지 않는다.
- **CONV-AC-09:** 프로젝트 보관 상태에서는 과거 자기 대화는 보이지만 새 메시지는 서버에서도 거부된다. 멤버십 회수 뒤에는 과거 조회도 거부된다.
- **CONV-AC-10:** 같은 대화의 `요청으로 정리`를 반복해도 요청 초안은 하나이며, 메시지 `좋아요`만으로 실행·발행 승인이 생기지 않는다.

현재 `devauto/api/main.py`는 Run 생성 중심이고 `devauto/core/db.py`의 `session_id`는 대화 소유권·메시지 이력을 표현하지 않습니다. 기존 필드를 이름만 바꿔 이 계약이 구현됐다고 판단하지 않습니다. 위 사례는 새 Django 도메인에 대한 구현·검증 목록이며 현재 통과 결과가 아닙니다.
