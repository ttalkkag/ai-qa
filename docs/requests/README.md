# 요청: 실행할 명세의 확정과 제출

> 상태: 로컬 Django 제품의 구현 계약. 현재 `devauto`의 실행 입력을 그대로 새 요청 도메인으로 인정하지 않습니다. 현재 코드와 목표 구현의 차이는 [문서 시작점](../README.md)에서 구분합니다.

## 1. 목적과 경계

사용자의 설명을 **어떤 문제를 어디까지 바꾸고 무엇으로 완료를 확인할지**가 명확한 작업 명세로 바꿉니다. 대화 내용 전체를 즉시 실행 지시로 전달하지 않습니다.

- [conversations](../conversations/README.md)는 설명·질문·답변을, 이 도메인은 초안·확정 명세·제출 기록을 소유합니다.
- [runs](../runs/README.md)는 확정 명세를 실제로 수행한 실행과 그 상태를 소유합니다. 요청 상태와 실행 상태를 합치지 않습니다.
- [accounts](../accounts/README.md)와 [projects](../projects/README.md)가 접근·대상 정책을, [ai](../ai/README.md)가 요구 구체화 호출을 결정합니다.
- 첨부와 사용자 결과 확인·관리자 로컬 승인은 [artifacts](../artifacts/README.md), 선택적 원격 발행은 [approvals](../approvals/README.md)를 따릅니다. 사용자 결과 확인과 관리자 승인을 구분해 기록합니다.

문서 도메인 이름은 `requests`, 제안 Django 앱 이름은 `apps.work_requests`입니다. 외부 Python 패키지 `requests`와 같은 이름의 최상위 앱을 만들지 않습니다.

## 2. 사용자 흐름과 화면

헤더의 `Request`(`/requests/`)에서 접근 가능한 요청 목록으로 들어갑니다. 요청 상세·실행·결과는 `Request`를 활성 메뉴로 유지하고 `Request / 요청 제목 / 실행 상태 / 변경 결과`처럼 네비게이션으로 연결합니다. 요청에서 `원래 대화`를 열면 프로젝트의 대화로 이동하므로 활성 메뉴는 `Project`가 됩니다. 매니저 사용 가이드는 공통 `Docs` 메뉴에 두며, 전체 화면 계약은 [내비게이션](../navigation/README.md)을 따릅니다.

1. 사용자는 대화에서 프로젝트와 현상·목표를 설명하고 `요청으로 정리`를 선택합니다.
2. AI가 코드를 읽고 초안을 제안합니다. 누락된 요구사항·관련 도메인·영향받는 코드/함수/엔드포인트/데이터·충돌/의도하지 않은 영향을 확인하고, 미확인 사실과 필수 질문을 구분합니다.
3. 사용자는 직접 수정하거나 대화로 보완합니다. AI 제안은 미확인 상태이고 사용자 확인 전까지 실행 명세가 아닙니다.
4. `명세 확인` 화면에서 최종 내용과 남은 불확실성, 수정 대상 프로젝트, 원본이 아닌 작업 사본을 사용한다는 안내를 확인합니다.
5. `이 명세로 준비`를 누르면 화면에서 확인한 코드 SHA·프로젝트 설정 버전·초안 버전을 재검사하여 변경 불가능한 명세 버전을 만듭니다. 그 사이 어느 값이든 바뀌면 새 기준을 표시하고 다시 확인하게 합니다. 아직 코드 수정은 시작하지 않습니다.
6. `수정 작업 시작`을 누르면 해당 버전에 대해 실행 1개를 접수하고 진행 화면으로 이동합니다. 코드·자료가 로그인된 Codex를 통해 외부 모델에 전달된다는 안내를 함께 제공합니다.
7. 실행 중 요구가 달라지면 `요청 보완`으로 새 초안을 저장합니다. 기존 실행에 새 조건을 조용히 섞지 않습니다.
8. 사용자는 실제 작업 보고와 변경 파일·검증 결과를 확인하고 `재수정 요청` 또는 `작업 완료 · 관리자에게 전달`을 선택합니다. 재수정은 기존 명세에 보완 내용을 추가한 새 초안이며, 다시 확정한 전체 요구사항을 기준 코드에서 새 워크트리로 실행합니다. 이전 패치 위에 자동으로 이어 쓰지 않습니다.
9. 사용자가 완료 확인한 최신 결과만 관리자가 로컬 승인하거나 보완을 요청합니다. 이 승인은 DB 기록만 변경하며 push·PR을 실행하지 않습니다. 원격 발행은 별도 설정·검토·승인이 필요합니다.

매니저에게 Git 브랜치·원격 주소·검증 명령·절대 경로·model/effort를 입력받지 않습니다. 프로젝트 운영 설정에서 정한 값을 읽기 쉬운 요약으로 보여주며 상세 기술정보는 접어서 제공합니다.
관리자의 `Admin / Approvals`은 사용자 확인을 마친 로컬 결과와 별도로 준비된 원격 발행을 검토하는 화면입니다. 요청자의 명세 확인·수정 시작 권한은 바뀌지 않습니다.

## 3. 명세 필드와 준비 조건

| 필드 | 준비 시 조건 | 안내 예시 |
|---|---|---|
| `title` | 필수, 1~200자 | `주문 취소 버튼 동작 수정` |
| `goal` | 필수, 바라는 결과를 한 가지 업무 단위로 표현 | `취소 가능한 주문은 버튼으로 취소할 수 있어야 함` |
| `current_behavior` | 버그라면 필수; 새 기능은 `현재 기능 없음` 가능 | `버튼을 눌러도 상태가 바뀌지 않음` |
| `expected_behavior` | 필수, 관찰 가능한 결과 | `확인 후 주문 상태가 취소로 바뀌고 안내가 보임` |
| `reproduction_steps` | 버그라면 재현 단계 또는 미확인 사유 | `내 주문 → 주문 상세 → 취소 클릭` |
| `acceptance_criteria` | 필수, 최소 1개 관찰 가능한 완료 조건 | `취소 불가 주문에는 취소 버튼이 나타나지 않음` |
| `scope` / `out_of_scope` | 수정 범위 필수, 제외 범위는 비어도 명시 | `주문 상세 화면만; 결제 환불 로직 변경 제외` |
| `unknowns` | 미확인 사실·가정과 영향 기록 | `특정 브라우저에서만 발생하는지는 미확인` |
| `related_domains` / `impact_analysis` / `conflict_analysis` | AI가 코드 근거로 분석하고 사용자가 확인·수정 가능; 기존 명세와의 호환을 위해 빈 값도 저장 가능 | `주문 도메인, cancel 함수와 상태 필드, 완료 주문 영향 없음` |
| `attachment_ids` | 선택, 허용된 본인 첨부만 | 오류 화면, 재현 설명 파일 |

초기 총 명세 본문 한도는 20,000자입니다. 서버가 길이·필수 필드·첨부 소속·자료 접근 가능 여부를 검증합니다. 형식 검사 통과와 요구사항의 의미가 충분하다는 판단을 혼동하지 않습니다.

수정 대상이나 완료 조건을 정할 수 없는 필수 질문이 남으면 준비를 막고 해당 항목만 다시 질문합니다. 재현 방법을 모르는 경우 미확인 사실과 가능한 검증 방법을 표시하여 사용자가 확인하게 합니다. AI가 답을 추측해 필수 항목을 채우지 않습니다.

사용자의 명세 확인은 프로젝트 정책 밖 파일·명령·네트워크 접근이나 원격 발행을 허용하지 않습니다. 범위를 넘는 요청은 설명을 보존한 채 거부 사유를 표시합니다.

## 4. 핵심 데이터와 불변 조건

| 객체 | 핵심 필드 | 불변 조건 |
|---|---|---|
| `WorkRequest` | `id`, `project_id`, `owner_id`, `conversation_id`, `state`, `draft_version` | 한 대화에 최대 1개, 프로젝트·원 소유자 유지 |
| 초안 필드 | 명세 필드, `ready_revision_id`, `latest_submitted_revision_id`, 작성·수정 시각 | 현재 편집 상태만 표현; 실행 결과로 본문을 덮어쓰지 않음 |
| `RequestRevision` | `id`, `request_id`, `number`, `source_draft_version`, 명세 스냅샷, `content_hash` | 준비 이후 명세 본문·첨부 참조 변경 금지; 요청 안에서 number·source_draft_version 각각 유일 |
| 준비 근거 | `confirmed_by_id`, `confirmed_at`, `project_config_version`, `base_commit_sha` | 확인 주체·시점·프로젝트 정책과 코드 기준을 기록 |
| 첨부 스냅샷 | `artifact_id`, 내용 해시 | 실행 중 같은 ID의 내용을 바꾸거나 다른 첨부로 치환하지 않음 |
| `RequestSubmission` | `revision_id`, `actor_id`, `submitted_at`, `idempotency_key`, `primary_run_id` | 한 revision의 최초 제출은 1건, primary run도 1개 |

`RequestRevision`은 **내용이 불변**입니다. 제출 여부는 별도 제출 기록으로 관리하므로 제출을 위해 확정 본문을 수정하지 않습니다. AI가 참고한 대화 메시지 범위도 revision에 연결하여 어떤 설명으로 준비했는지 추적합니다.

`base_commit_sha`는 사용자가 준비 화면을 확인한 로컬 Git 기준입니다. 실제 작업 사본 생성·검증은 runs가 수행하며, 확인 당시 SHA를 다른 SHA로 몰래 대체하지 않습니다. 원본의 미커밋 변경은 보존하고 실행 입력에서 제외합니다. 준비 화면에 이 사실을 안내하며, 유효한 committed SHA가 있다면 dirty 상태만으로 제출을 막거나 매니저에게 Git 정리를 요구하지 않습니다.

확인 화면은 서버가 읽은 `expected_project_config_version`과 `expected_base_commit_sha`를 초안 버전과 함께 전달합니다. 확인 POST에서 값의 형식·소속·현재값을 재검사하며 클라이언트 값만 믿지 않습니다. 명세 확정 직후 ref가 다시 이동하는 경쟁은 제출/claim 시 재검사로 차단합니다. 확인과 실행 사이 원본 branch가 잠긴다고 보장하지 않습니다.

## 5. 요청 상태와 버전

| 현재 상태 | 의미 | 허용되는 다음 행동 |
|---|---|---|
| `DRAFT` | 요구 보완 중, 실행 불가 | 저장·AI 제안 적용·명세 확인 후 `READY` |
| `READY` | 사용자가 확인한 불변 revision이 있음, 미제출 | 해당 revision 제출하여 `SUBMITTED`, 또는 보완하여 `DRAFT` |
| `SUBMITTED` | 해당 revision의 최초 실행이 접수됨 | 진행·결과 조회, 기존 실행 종료 후 명시적 재시도, 새 명세 보완 |

- WorkRequest의 상태는 **현재 편집 흐름**입니다. 새 초안을 열어 `DRAFT`가 되어도 이전 revision의 제출·실행 이력은 남습니다.
- `READY → DRAFT`에서 기존 revision을 편집하지 않습니다. 초안만 바꾸고 다시 준비하면 revision 번호가 증가합니다.
- 기준 SHA·실행 설정만 바뀌어 본문을 고칠 필요가 없을 때는 `준비 기준 새로고침`으로 본문을 유지한 채 `draft_version`을 증가시키고 DRAFT로 전환합니다. 새 근거를 표시한 뒤 다시 확인하면 새 revision을 만듭니다. 동일 draft_version의 멱등 확정이 오래된 기준만 계속 반환하는 막힌 경로를 만들지 않습니다.
- `SUBMITTED → DRAFT`도 같은 규칙입니다. 실행 중 새 초안 작성은 허용하지만 현재 Run은 원래 revision만 읽습니다.
- 실행의 `FAILED`, `CANCELLED`, `INTERRUPTED`, `SUCCEEDED`는 Run 상태입니다. 이를 요청의 제출 이력 삭제나 자동 초안 복귀로 처리하지 않습니다.
- 한 요청에는 활성 Run을 최대 1개만 허용합니다. 새 revision이 준비돼도 기존 실행 종료 전 제출은 거부합니다.
- 요청 보완으로 과거 결과·승인을 새 revision에 복사하지 않습니다. 어떤 결과·버전에 대한 확인인지는 approvals가 검증합니다.

## 6. 제출·중복·재시도 계약

`submit(actor, request_id, revision_id, idempotency_key)`는 아래를 한 번의 원자적 접수로 처리합니다.

1. 활성 계정·프로젝트 접근권한·요청 소유권, 프로젝트 활성 상태와 revision의 소속 관계를 확인합니다. ADMIN도 타인의 요청을 대신 확정·제출·재시도하지 않습니다.
2. 같은 키가 이미 처리됐다면 같은 제출·Run을 반환합니다. 같은 키로 다른 revision이나 payload를 보내면 충돌로 거부합니다.
3. 이미 제출된 revision은 다른 키여도 기존 primary Run을 반환하며 두 번째 실행을 만들지 않습니다. 이 중복 확인은 현재 READY 상태 검사보다 먼저 하여 정상 재전송을 허용합니다.
4. **최초 접수일 때만** 현재 READY 버전인지, 활성 Run이 없는지, 확인된 정책 버전·기준 SHA가 여전히 유효한지 검사합니다.
5. 요청 상태·제출 기록·Run·작업 등록을 같은 DB 트랜잭션으로 반영합니다. 경합은 revision별 유일 제약·상태 조건부 갱신으로 막고, 중간 실패 시 일부만 남지 않습니다.

실패한 **실행의 재시도**는 최초 제출과 다른 동작입니다. `retry_run(actor, previous_run_id, idempotency_key)`는 runs가 소유합니다.

- 이전 Run이 `SUCCEEDED/FAILED/CANCELLED/INTERRUPTED` 중 하나인 terminal 상태일 때만 접수합니다. 취소 요청 중은 terminal이 아닙니다.
- 같은 확정 revision·같은 기준 SHA의 작업을 다시 수행하는 새 Run을 만들고 `previous_run_id`를 기록합니다. 최초 Run을 재사용·초기화하지 않습니다.
- 성공한 실행도 같은 요구를 처음부터 다시 시도할 수 있으나, 기존 결과의 검증만 다시 하는 동작은 아닙니다. 새 Codex 호출의 결과가 달라질 수 있음을 표시합니다. 원하는 결과나 수정 범위가 바뀌면 재시도가 아니라 새 revision입니다.
- 프로젝트 설정·기준 SHA가 바뀌었으면 재시도하지 않고 새 revision 확인으로 안내합니다. 최신 원본을 같은 명세 버전의 기준으로 슬쩍 바꾸지 않습니다.
- 재시도 버튼은 `요청 v1 그대로 다시 실행`처럼 대상 버전을 표시합니다. 더 최신 초안이 있어도 그 내용을 섞지 않습니다.
- 자동 재제출·무한 재시도·과거 발행 승인 재사용은 금지합니다. 재시도 중복 키도 새 Run을 1개만 만듭니다.

## 7. 서버 Interface와 코드 배치

아래는 Django form·서비스의 구현 계약입니다. 자동 검사의 범위와 실제 AI를 포함한 미검증 흐름은 [검증 기록](../operations/verification.md)을 따릅니다. 모든 변경은 POST + 로그인 세션 + CSRF이며 GET으로 준비·제출하지 않습니다.

| 진입점 | 서비스와 주요 인자 |
|---|---|
| 대화의 `POST /conversations/{id}/request/` | `create_or_get_draft(actor, conversation_id)`; 요청만 생성, 수정 실행 없음 |
| `GET /requests/` / `GET /requests/{id}/` | 허용된 내 요청 목록 / 초안·버전·실행 요약 |
| `POST /requests/{id}/draft/` | `save_draft(actor, id, expected_draft_version, fields)` |
| `POST /requests/{id}/refresh-basis/` | `refresh_basis(actor, id, expected_draft_version, idempotency_key)`; 본문 유지·초안 버전 증가·새 기준 표시, 자동 확정/제출 없음 |
| `POST /requests/{id}/clarify/` | `suggest_revision(actor, id, expected_draft_version, idempotency_key)`; AI 제안만 생성 |
| `POST /requests/{id}/ready/` | `confirm_revision(actor, id, expected_draft_version, expected_project_config_version, expected_base_commit_sha)`; 표시한 기준 재검사 후 불변 revision 생성 |
| `POST /requests/{id}/submit/` | `submit(actor, id, revision_id, idempotency_key)` |
| 실행의 `POST /runs/{id}/retry/` | runs의 `retry_run`으로 위임 |

- 두 탭에서 초안을 편집하면 `expected_draft_version` 비교로 오래된 저장·확정을 거부합니다. 최신 내용을 덮어쓰지 않고 다시 확인하게 합니다.
- 초안 버전·expected 설정 버전·expected 기준 SHA가 모두 같은 준비 요청의 재전송·경합만 동일 revision을 반환합니다. 같은 draft_version에 다른 준비 근거를 보내면 `409`와 `refresh-basis` 안내를 반환합니다. 재확인만으로 내용이 같은 버전 두 개를 만들지 않습니다.
- AI 제안이 늦게 도착해도 대상 draft_version이 바뀌었다면 자동 적용하지 않습니다. 제안 생성과 사용자 채택을 분리합니다.
- 권한 검사·revision 소속 검사·중복 방지는 서비스 안에 두어 HTML 이외 진입점도 같은 계약을 사용하게 합니다.
- 경합 제어는 DB 유일 제약과 상태·버전 조건부 갱신으로 보장합니다. SQLite에서 행 잠금 지원을 가정하여 중복 제출을 방치하지 않습니다.
- 제안 코드: `apps/work_requests/{models,forms,views,services,urls}.py`, `templates/work_requests/`.

## 8. 거부·오류와 복구 안내

| 상황 | 처리와 사용자 안내 |
|---|---|
| 다른 사용자 요청·다른 프로젝트 revision | 존재 여부를 노출하지 않는 접근 거부; Run·작업 생성 0건 |
| 보관된 프로젝트 | 과거 요청·결과는 조회 가능, 초안 변경·명세 확인·제출은 거부 |
| 멤버십 회수·계정 정지 | 과거 조회·새 동작 모두 거부; 원래 자료를 삭제하지 않음 |
| 초안 버전 충돌 | `다른 화면에서 내용이 바뀌었습니다. 최신 내용을 확인해 주세요.`; 충돌 응답 |
| 기준 코드·정책 변경 | `준비 당시 프로젝트 상태가 바뀌었습니다. 명세를 다시 확인해 주세요.` |
| Codex·실행 준비 불가 | 원인을 표시하고 접수를 거부하거나, 접수 이후라면 Run에 실패를 기록; 성공으로 표시하지 않음 |
| 같은 요청의 실행 진행 중 | 기존 진행 화면으로 안내; 별도 실행 추가 생성 거부 |
| 첨부 삭제·해시 불일치 | 준비·제출 차단; 파일을 다시 선택하고 새 revision 확인 |

## 9. 결정 사항과 대안

| ID | 구분 | 채택안과 이유 | 제외한 대안 |
|---|---|---|---|
| REQ-01 | 사용자 요구 | 자연어 요구 구체화 후 명시적 작업 시작 | 일반 대화 저장 즉시 코드 수정 |
| REQ-02 | 사용자 요구 | 매니저는 작업 요청, 관리자만 별도 발행 승인 | 명세 확인을 push·PR 승인으로 겸용 |
| REQ-03 | 구현 초기값 | `DRAFT → READY → SUBMITTED`와 불변 명세 버전 | 실행 중에도 같은 명세 행을 덮어쓰기 |
| REQ-04 | 구현 초기값 | 최초 제출 1개 + 명시적 새 Run 재시도 | 더블클릭·재접속·실패 복구마다 묵시적으로 새 실행 |
| REQ-05 | 구현 초기값 | 같은 요청의 보완은 새 revision, 별도 업무는 새 요청 | 모든 대화를 한 개 무기한 변경 요청으로 합치기 |

## 10. 검증 사례

- **REQ-AC-01:** 프로젝트·문제 설명에서 시작해 명세를 보완하고, `수정 작업 시작` 이전에는 작업 사본 변경이 발생하지 않는다.
- **REQ-AC-02:** 필수 목표·완료 조건이 비어 있으면 READY가 되지 않으며, AI 추측으로 빈 항목을 채우지 않는다.
- **REQ-AC-03:** 준비 뒤 수정하면 새 draft가 되고 기존 revision 본문·첨부 해시는 동일하다. 다시 확인하면 새 revision이 생긴다.
- **REQ-AC-04:** 동일·상이한 중복 키의 동시 최초 제출에도 primary Run·작업이 1개만 생성된다. 같은 키의 다른 요청 내용은 거부된다.
- **REQ-AC-05:** 실행 중 새 초안을 저장해도 기존 Run의 revision·기준 SHA·명세 해시가 바뀌지 않는다. 두 번째 활성 실행은 생성되지 않는다.
- **REQ-AC-06:** 실패·취소 완료 뒤 재시도하면 같은 revision의 새 Run과 previous_run 참조가 생기고 원래 결과·오류는 보존된다.
- **REQ-AC-07:** 기준 SHA 또는 프로젝트 설정 버전 변경 후 제출·재시도를 막고 새 명세 확인을 요구한다.
- **REQ-AC-08:** 다른 매니저의 요청·revision·첨부 ID 변조는 서버에서 거부되며 AI 호출·Run·발행 기록이 생기지 않는다.
- **REQ-AC-09:** 오래된 탭 저장 또는 늦은 AI 제안이 최신 초안을 덮어쓰지 않는다.
- **REQ-AC-10:** 취소 요청 중인 Run의 재시도를 거부한다. 성공 결과의 수정 요구는 새 revision으로 접수하며 과거 승인을 승계하지 않는다.
- **REQ-AC-11:** 확인 화면을 연 뒤 SHA·정책이 바뀌면 확정 POST를 거부한다. 본문을 바꾸지 않은 `준비 기준 새로고침`과 재확인으로 새 기준의 revision을 만들고 제출할 수 있다. 새로고침 중복 요청은 초안 버전을 반복 증가시키지 않는다.

현행 `RunCreate`와 `Database.create_run`은 제목·설명에서 Run을 직접 만드는 구조입니다. 이 문서의 분리된 요청 모델·계정 소유권·불변 revision·멱등 제출 검증은 새 구현 대상이며 기존 테스트 통과만으로 완료 처리하지 않습니다.
