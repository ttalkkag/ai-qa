# 계정과 접근 권한

> 상태: 로컬 Django 제품의 구현 기준. 이 문서는 구현 완료나 보안 검증 통과를 뜻하지 않습니다.

## 1. 목적과 책임

앱을 쓰는 사람을 계정으로 식별하고, 요청·실행·결과·발행에 접근할 수 있는 범위를 서버에서 결정합니다.
접속한 PC·휴대폰·IP, 서버를 실행한 OS 사용자, Codex 로그인 주체는 앱의 권한이 아닙니다.

이 도메인이 소유하는 것은 앱 계정, 로그인 세션, `ADMIN`/`MANAGER` 역할, 프로젝트 멤버십, 객체 접근 판정, 계정 변경 감사 기록입니다.
다른 도메인은 역할 문자열을 각자 비교하지 않고 이 도메인의 Interface로 현재 권한을 확인합니다.

다음 항목은 소유하지 않습니다.

- 저장소 경로와 실행 정책: [프로젝트](../projects/README.md).
- 요청 내용과 소유 요청의 작업 상태: [요청](../requests/README.md), [실행](../runs/README.md).
- 결과 조회: [결과물](../artifacts/README.md). 발행 승인·Git 작업의 유효성: [승인과 발행](../approvals/README.md).
- Codex 인증정보와 모델 설정: [AI](../ai/README.md).
- 서버 주소·HTTPS·로컬 데이터 디렉터리: [운영](../operations/README.md).

## 2. 역할과 허용 범위

| 행동 | MANAGER | ADMIN |
| --- | --- | --- |
| 프로젝트 목록 | 멤버십이 있는 프로젝트 | 전체 프로젝트 |
| 대화·요청 생성 | 할당된 활성 프로젝트 | 활성 프로젝트 |
| 대화·요청·실행·결과 조회 | 멤버십이 있고 자신이 소유한 요청 계열 | 전체; 운영 목적의 접근도 기록 |
| 명세 확정·수정 실행·재시도·취소 | 자신의 요청 | 자신의 요청; 다른 요청의 운영 취소만 별도 사유로 허용 |
| 다른 사용자 대신 명세 확인·수정 제출 | 불가 | 불가; 운영자 검토와 요청자의 명세 확인은 구분 |
| 발행 승인·반려·push·PR 요청 | 불가 | 승인 도메인이 정한 추가 조건을 만족할 때만 가능 |
| 본인 아이디 조회, 닉네임·비밀번호 변경 | 가능 | 가능 |
| 타인 계정·역할·멤버십·프로젝트·모델 정책 변경 | 불가 | 가능 |

`ADMIN`은 운영하는 모든 프로젝트에 접근합니다. 관리자에게 별도 멤버십을 만들 필요는 없습니다.
`MANAGER`의 멤버십은 프로젝트 사용 허가이지 다른 매니저의 요청을 열람하는 허가는 아닙니다.
관리자가 만든 요청도 소유자를 명시하며, 권한이 있다고 타인의 이름으로 확인한 것으로 기록하지 않습니다. 결과 의도 확인을 별도 승인 단계로 만들지는 않습니다.

## 3. 사용자 흐름과 화면

### 최초 관리자

1. 서버 운영자가 터미널에서 `python manage.py bootstrap_admin`을 실행합니다.
2. 로그인 아이디(사용자 이름)와 숨김 입력 비밀번호를 지정합니다. 이메일은 사용하지 않으며 발송 기능도 없습니다.
3. 명령은 앱 역할 `ADMIN`을 명시적으로 부여하고, 생성한 계정 ID·사용자 이름만 출력합니다.
4. 브라우저 로그인 후 프로젝트를 등록하고 매니저 계정·멤버십을 설정합니다.

이 명령은 이미 존재하는 계정을 조용히 관리자 승격하거나 비밀번호를 덮어쓰지 않습니다.
명령 이름과 입력 방식은 구현 기본값이며, Django 관리 화면 접근 권한과 제품 역할을 혼동하지 않게 합니다.

### 매니저 첫 사용

1. 관리자가 사용자 이름·표시 이름·역할·초기 비밀번호·할당 프로젝트로 계정을 만듭니다.
2. 초기 비밀번호는 관리자가 사용자에게 직접 전달합니다. 앱은 메일·메신저로 보내지 않습니다.
3. 사용자는 로그인 후 초기 비밀번호를 변경해야 프로젝트에 접근할 수 있습니다.
4. 프로젝트 목록에는 허용된 프로젝트만 표시합니다. 없으면 `할당된 프로젝트가 없습니다. 관리자에게 문의하세요`를 표시합니다.
5. 이후 요청 화면에서는 역할·프로젝트 ID·소유자 ID·CLI 설정을 직접 입력하지 않습니다.

### 화면별 필수 입력

| 화면 | 필수 입력 | 노출하지 않는 항목 |
| --- | --- | --- |
| 로그인 | 사용자 이름, 비밀번호 | API 키, Codex 토큰, 공유 접근 토큰 |
| Account 내 정보 | 아이디 읽기 전용, 닉네임 필수 | 이메일, 역할·프로젝트 목록, 타인 계정, 로그인 ID 변경 |
| 비밀번호 변경 | 현재 비밀번호, 새 비밀번호, 확인 | 비밀번호 해시 |
| 관리자 계정 생성 | 사용자 이름, 표시 이름, 역할, 초기 비밀번호 | OS 계정 생성, Codex 계정 생성 |
| 관리자 권한 편집 | 대상 계정, 역할 또는 활성 상태, 변경 사유 | `is_staff`를 발행 권한으로 사용하는 옵션 |
| 프로젝트 할당 | 대상 계정, 프로젝트, 추가/회수, 변경 사유 | 다른 요청의 소유권 변경 |

자신의 `Account` 화면에는 아이디 확인, 닉네임 편집, `내 정보 저장`, `비밀번호 변경`, 하단 `로그아웃`만 둡니다. 이메일·역할·할당 프로젝트·타인 계정 목록이나 관리자에게 문의하라는 빈 프로젝트 안내는 표시하지 않습니다. 프로젝트는 `Project`에서 확인하며 다른 사용자 관리는 `Admin` → `계정 관리`에만 둡니다.
아이디는 로그인용 고유 `username`이고 읽기 전용입니다. 닉네임은 별도의 `display_name`으로 1~100자 필수이며 로그인 ID·권한과 무관합니다. 닉네임만 저장할 때에는 세션을 유지하고, 비밀번호 변경은 기존 현재 비밀번호 확인·최소 6자·재로그인 절차를 따릅니다. 이메일은 입력·조회·로그인·인증·복구에 사용하지 않습니다. Django 기본 email 필드와 기존 값은 호환성을 위해 DB에 보존하되 Account에서 읽거나 변경하지 않습니다.

현재 로컬 확인 계정은 관리자 `admin`(닉네임 `관리자`), 매니저 `guest`(닉네임 `게스트`)입니다. 사용자가 지정한 로컬 시험 비밀번호를 사용하며 신규 설치의 기본 공통 비밀번호로 코드에 내장하지 않습니다.
관리자 설정은 일반 요청 화면과 분리하되, 숨겨진 메뉴만으로 접근 통제가 되었다고 판단하지 않습니다.

헤더의 설정 아이콘 `Account`는 모든 로그인 사용자의 `/accounts/me/`로 연결합니다. 비밀번호 변경도 `Account`를 활성 메뉴로 유지합니다. 관리자 전용 계정 관리는 `Admin` → `계정 관리`(`/accounts/manage/`)로 접근하고, 네비게이션은 `Admin / Users`로 표시합니다. 헤더에 로그아웃 버튼을 두지 않으며, 내 계정 본문 맨 아래에 작은 `로그아웃` 버튼을 둡니다. 로그아웃은 기존처럼 CSRF가 있는 POST이고 GET 링크로 바꾸지 않습니다.

매니저에게 `AI`·`Admin` 헤더 메뉴는 보이지 않습니다. URL을 직접 입력한 관리자 화면 접근도 서버에서 거부합니다. `Docs`(`/docs/`)와 `Account`는 로그인 사용자 공통 메뉴이며, 초기 비밀번호 변경 요구·세션 만료·비활성 계정 등 기존 접근 조건을 우회하지 않습니다. 메뉴와 경로의 전체 계약은 [내비게이션](../navigation/README.md)을 따릅니다.

## 4. 핵심 데이터

| 데이터 | 필수 값과 규칙 |
| --- | --- |
| `User` | 불변 ID, 고유 username(아이디), display_name(닉네임), password hash, role, is_active, must_change_password, authz_version, created_at. Django email은 호환용 미사용 필드 |
| `ProjectMembership` | user_id, project_id, granted_by, created_at; 사용자·프로젝트 조합은 하나 |
| `AccountAudit` | actor_id 또는 bootstrap 식별, action, subject_id, project_id 선택, 비밀정보 없는 변경 전후 값, reason, created_at |
| 로그인 세션 | user_id, 발급·만료 정보, 로그인 당시 authz_version; 비밀번호·Codex 자격증명은 저장하지 않음 |

계정 ID는 요청·승인의 작성자 기록에 사용합니다. 표시 이름 변경으로 과거 행위자가 바뀌지 않습니다.
계정은 비활성화하며 사용 이력이 있는 계정의 물리 삭제·다른 사람으로의 ID 재사용은 제공하지 않습니다.
프로젝트 멤버십을 회수해도 요청과 결과는 보존합니다. 재할당 전에는 해당 매니저가 다시 읽을 수 없습니다.
비밀번호 원문·초기 비밀번호·세션 쿠키는 감사 기록이나 로그에 저장하지 않습니다.

## 5. 서버 Interface

아래 작업명은 같은 Django 프로젝트 내부의 Interface입니다. 별도 인증 서버나 범용 권한 엔진을 만들지 않습니다.

| 작업 | 입력 | 결과와 주요 오류 |
| --- | --- | --- |
| `authenticate` | username, password | 로그인 주체; `INVALID_CREDENTIALS`, `LOGIN_THROTTLED` |
| `require_access` | 서버가 확인한 actor, action, project_id, 대상 객체 선택 | 허용 또는 `AUTH_REQUIRED`, `ACCESS_DENIED`, `NOT_FOUND` |
| `list_accessible_projects` | actor | 권한 필터가 적용된 목록; 비활성 계정은 거부 |
| `create_account` | admin, username, display_name, role, initial_password | 새 계정; `USERNAME_TAKEN`, `INVALID_INPUT` |
| `change_account` | admin, target_id, expected_authz_version, 변경값, reason | 갱신 계정; `VERSION_CONFLICT`, `LAST_ADMIN_REQUIRED` |
| `set_membership` | admin, user_id, project_id, granted, reason | 갱신 멤버십; `NOT_FOUND`, `ACCESS_DENIED` |
| `update_profile` | 로그인 actor, display_name | 본인 닉네임만 갱신, 아이디·세션 유지; `INVALID_INPUT`, `VERSION_CONFLICT` |
| `change_password` | actor, current_password, new_password | 새 로그인 필요; `INVALID_CREDENTIALS`, `WEAK_PASSWORD` |
| `reset_password` | admin, target_id, new_temporary_password, reason | 강제 변경 상태; 기존 세션 폐기 |
| `logout` | 현재 세션 | 해당 세션 폐기; 반복 요청도 추가 효과 없음 |

인증되지 않은 HTML 요청은 로그인으로 이동하고, JSON 요청은 401을 반환합니다.
타인의 요청 ID·존재를 알아낼 수 있는 조회는 존재하지 않는 대상과 같은 404를 반환합니다.
대상은 알지만 역할상 금지된 발행·운영 작업은 403을 반환합니다. 오류 문자열은 내부 경로나 계정 존재 여부를 불필요하게 노출하지 않습니다.

## 6. 상태와 강제 규칙

계정 상태는 활성/비활성, 초기 비밀번호 변경 필요 여부로 표현합니다. 역할과 계정 활성 상태를 하나의 값으로 합치지 않습니다.

- 공개 회원 가입은 없습니다. 최초 bootstrap 이후 계정 생성·권한 변경은 `ADMIN`만 수행합니다.
- 마지막 활성 `ADMIN`을 비활성화하거나 강등하는 요청은 한 트랜잭션 안에서 거부합니다.
- 로그인 성공만으로 접근을 확정하지 않습니다. 요청마다 DB의 활성 상태·역할·멤버십·소유권을 확인합니다.
- 역할·활성 상태·멤버십 변경은 `authz_version`을 증가시킵니다. 기존 세션은 다시 로그인하도록 처리합니다.
- 이미 열린 화면의 후속 polling, 이벤트 목록 재조회, 결과 다운로드도 같은 권한 검사를 통과해야 합니다.
- 대기 작업 claim 직전과 발행 직전에도 현재 행위자 권한을 재확인합니다. HTTP 요청 시 허용됐다는 사실만 재사용하지 않습니다.
- 실행 중 행위자의 권한이 회수되면 실행 도메인에 취소를 요청합니다. 프로세스 종료 확인 전 취소 완료로 표시하지 않습니다.
- 모든 상태 변경 HTTP 요청에는 Django 세션 인증과 CSRF 검사를 적용하며 GET으로 변경하지 않습니다.
- username, owner_id, role을 브라우저 값으로 신뢰하지 않습니다. 새 대화·요청의 소유자는 로그인한 계정에서 정합니다.
- Account의 변경 대상은 로그인 계정으로 고정하고 닉네임만 허용합니다. 요청 본문에 email·target_id·role·username 등이 포함되어도 이메일·타인 계정·권한·아이디를 변경하지 않습니다.
- 프로젝트 아카이브 후 과거 조회는 기존 접근 권한 안에서 유지합니다. 신규 대화·실행 허용 여부는 프로젝트 도메인이 판정합니다.

계정 권한과 프로세스 권한은 다릅니다. 매니저의 HTTP 발행 요청 거부는 Codex가 Git 인증정보를 사용할 수 없다는 증거가 아닙니다.
실행·발행 자격 분리는 AI 및 승인 도메인의 별도 인수조건입니다.

## 7. 확정 요구와 구현 기본값

| ID | 구분 | 결정 |
| --- | --- | --- |
| ACC-01 | 사용자 확정 | 승인·권한은 계정 단위이며 기기·네트워크·호스트 여부와 독립적이다 |
| ACC-02 | 사용자 확정 | 매니저에게 push·PR 생성 권한을 부여하지 않고 관리자만 승인·발행할 수 있다 |
| ACC-03 | 구현 기본값 | ADMIN은 전체 프로젝트 운영, MANAGER는 멤버십과 자기 소유 요청만 접근한다 |
| ACC-04 | 구현 기본값 | Django 세션·사용자 이름/비밀번호, 공개 가입·메일 인증·OAuth·공유 토큰 없이 시작한다 |
| ACC-05 | 구현 기본값 | 서버에서 로그인 후 최대 12시간을 강제하고 브라우저 세션 쿠키 사용; 비밀번호·권한 변경 시 기존 세션 무효화 |
| ACC-06 | 구현 기본값 | 로그인 5회 연속 실패 시 해당 사용자 이름·접속 주소 조합을 5분 제한하며 존재 여부는 숨긴다 |
| ACC-07 | 구현 기본값 | `bootstrap_admin`으로 최초 계정을 만들고 마지막 활성 관리자를 보호한다 |
| ACC-08 | 사용자 확정 | 현재 내부 사용 환경의 비밀번호 조건은 6자 이상만 적용한다. 문자 조합, 흔한 비밀번호, 사용자 이름과의 유사성은 제한하지 않는다 |
| ACC-09 | 사용자 확정 | 개인 계정은 공통 Account 아이콘, 사용자·소속 관리는 ADMIN 전용 Admin 하위로 구분하며 로그아웃은 계정 화면 하단에 둔다 |
| ACC-10 | 사용자 확정 | Account는 본인의 아이디 확인·닉네임/비밀번호 변경만 제공하며 이메일은 제거한다. 프로젝트·타인 관리와 구분하고 하단 로그아웃은 유지한다 |

비밀번호는 Django의 안전한 해시·검증 기능으로 관리합니다. 세션 쿠키는 HttpOnly·SameSite=Lax를 적용합니다.
최초 관리자 생성, 관리자에 의한 계정 생성·비밀번호 재설정, 사용자 비밀번호 변경에 같은 6자 이상 조건을 적용합니다. `123456`처럼 숫자로만 구성된 비밀번호도 허용하며, 초기 비밀번호 강제 변경·기존 세션 무효화·계정별 접근 권한은 유지합니다.
추후 외부 접근을 허용할 때의 비밀번호 조건은 8자 이상·영어 대문자 1개 이상·특수문자 1개 이상입니다. 이는 후속 구현 사항으로 현재 적용하지 않으며, 접속 주소에 따라 비밀번호 정책을 자동 전환하지 않습니다. 이번 비밀번호 조건 변경은 서버의 공개 범위나 네트워크 설정을 변경하지 않습니다.
Secure 쿠키와 HTTPS 적용은 [운영](../operations/README.md)의 loopback/LAN 설정을 따르며, loopback HTTP 예외를 LAN으로 확대하지 않습니다.
브라우저의 세션 복원 기능은 종료 뒤에도 쿠키를 복원할 수 있으므로 창을 닫는 것을 확실한 로그아웃으로 보장하지 않습니다. `issued_at` 기준의 절대 12시간 제한과 명시적 로그아웃은 서버가 강제하고 polling으로 연장하지 않습니다. 이 구분은 [Django 세션 문서](https://docs.djangoproject.com/en/5.2/topics/http/sessions/)를 따릅니다.
구현 기본값은 사용자 확정 발언이 아닙니다. 권한을 확대하거나 공개 가입을 추가하는 변경은 별도 결정이 필요합니다.

## 8. 인수조건

- [ ] ACC-AC-01: 같은 PC의 별도 세션에서 매니저와 관리자를 구분하고, 접속 주소를 바꿔도 역할은 바뀌지 않는다.
- [ ] ACC-AC-02: 매니저는 미할당 프로젝트와 다른 사람의 요청·실행·결과·이벤트·다운로드를 열 수 없다.
- [ ] ACC-AC-03: 매니저의 발행 승인·push·PR·정책 변경 직접 요청은 거부되고 대기 작업·외부 부작용이 0건이다.
- [ ] ACC-AC-04: 계정 정지·역할 변경·멤버십 회수 직후 기존 세션과 대기 작업의 권한이 다시 평가된다.
- [ ] ACC-AC-05: 동시 요청으로 마지막 활성 관리자를 모두 제거할 수 없고 감사 기록에 변경 주체가 남는다.
- [ ] ACC-AC-06: CSRF 없는 변경 요청·GET 변경·owner_id/role 변조를 거부하고 DB 상태가 보존된다.
- [ ] ACC-AC-07: 초기 비밀번호 강제 변경, 로그아웃, 비밀번호 재설정, 세션 만료가 실제 HTTP 검사로 확인된다.
- [ ] ACC-AC-08: 비밀번호·세션·Codex 토큰이 HTML·오류·감사 로그에 남지 않는다.
- [ ] ACC-AC-09: 비밀번호를 지정하는 모든 경로에서 6자 미만은 거부하고, 6자 이상은 숫자 전용·흔한 값·사용자 이름과 유사한 값이라는 이유로 거부하지 않는다.
- [ ] ACC-AC-10: 매니저에게 AI·Admin 메뉴가 없고 관리자 URL 직접 요청도 거부된다. Account·Docs는 로그인 조건을 유지하며, 하단 로그아웃의 POST·CSRF·세션 폐기 동작은 보존된다.
- [ ] ACC-AC-11: ADMIN·MANAGER 모두 Account에서 본인 아이디를 확인하고 닉네임을 저장·재조회할 수 있다. 이메일은 노출하지 않는다. 닉네임 오류·CSRF 없는 요청은 저장되지 않고, 이메일·아이디·대상·권한 값 변조는 타인 계정·역할·비밀번호·아이디·이메일에 영향을 주지 않는다.

현재 `devauto/api/main.py`는 선택적 공유 토큰과 공통 승인 경로를 사용합니다. 위 계정별 정책이 이미 구현됐다고 취급하지 않습니다.
