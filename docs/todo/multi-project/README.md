# MP-001 · 멀티 프로젝트 공동 작업

> 작성·조사: 2026-09-17
> 상태: 조사 정리 완료, 설계 미확정, 미구현
> 아래 권장안은 구현 승인이나 확정된 제품 계약이 아니다

## 1. 요청과 목표

프로젝트 추가 시 백엔드·프론트엔드처럼 연결된 프로젝트를 함께 등록하고, 하나의 요청으로 관련 코드를 분석·수정·검증할 수 있어야 한다
여러 프로젝트가 동시에 메인일 수 있으며, 어디서 분석을 시작할지와 실제 명령을 어디서 실행할지는 구분해야 한다

관리자는 연결 관계·권한·환경·검증 조건을 준비하고, 매니저는 서비스에서 바라는 변화와 결과만 설명한다
매니저에게 저장소 경로, 작업 순서, Docker 설정이나 모델 ID를 매번 입력하게 하지 않는다

이번 작업은 조사와 TODO 작성이다. 코드·DB·기존 등록 프로젝트·로컬 실행 상태를 변경하지 않는다

## 2. 현재 구현과 차이

현재 프로젝트를 여러 개 등록하는 것은 가능하지만, **하나의 요청으로 여러 프로젝트를 공동 수정하는 모델은 없다**

| 영역 | 현재 코드에서 확인한 구조 | 멀티 프로젝트에서 필요한 변화 |
| --- | --- | --- |
| 프로젝트 | Project에 고유한 저장소 경로 하나 | 기존 저장소 등록과 여러 프로젝트의 연결을 분리 |
| 권한 | 사용자 역할 + 프로젝트 멤버십 + 요청 소유자 | 요청에 포함된 모든 대상에 같은 기준 적용 |
| 대화·요청 | Conversation·WorkRequest가 Project 하나 참조 | 공동 문맥과 프로젝트별 영향을 담는 대상 목록 |
| 확정 명세 | 기준 SHA·프로젝트 설정 버전 각각 하나 | 대상별 기준 코드·설정과 그룹 구성 버전 고정 |
| 실행 | Run의 프로젝트·작업 사본·결과 커밋 각각 하나 | 하나의 요청 진행 상태 아래 대상별 실행 기록 |
| 컨테이너 | 하나의 workspace를 기준으로 cwd·마운트 검사 | 대상별 경로 판정과 공동 실행 환경 |
| 결과·승인 | 하나의 실행 결과와 manifest hash 기준 | 대상별 결과 + 연동 검증을 포함한 통합 hash |

상세 근거와 외부 참고 자료는 [조사 기록](research.md)에 있다
단순히 Path를 여러 개 받거나 저장소들의 상위 폴더를 통째로 마운트하는 것으로 해결하지 않는다

## 3. 도메인과 작업 시작점 — 권장안

기존 Project는 유지하고, 관련 Project를 연결하는 **작업 그룹**을 추가한다
화면은 기존 `Project` 메뉴 안에서 단일 프로젝트와 그룹을 구분하고, 새 최상위 메뉴를 늘리지 않는 방향을 권장한다
용어 정의는 [제안 용어](CONTEXT.md)를 따른다

| 구분 | 예시 | 의미와 제한 |
| --- | --- | --- |
| 그룹 | 고객 서비스 | 백엔드·프론트엔드를 함께 선택하는 업무 단위 |
| 구성원 | backend, frontend, contracts | 기존 프로젝트 ID를 연결, 별칭은 그룹 내 고유 |
| 메인 | backend와 frontend 모두 | 주요 대상 표시, 단일 선택 강제 없음 |
| 참여 한도 | 수정 가능 / 참조 전용 | 프로젝트 정책보다 넓힐 수 없음, 메인과 독립 |
| 분석 시작점 | 미지정 또는 frontend | 관리자 선택 힌트, 지정하지 않아도 동작 |
| 실행 위치 | backend 검사 명령의 cwd | 명령마다 대상 프로젝트와 상대 경로를 명시 |
| 실행 의존 관계 | API 계약 확정 → 타입 생성 → UI 검증 | 메인 순서가 아니라 작업에 필요한 의존 관계 |

두 프로젝트가 모두 메인이어도 둘 다 항상 수정하지는 않는다. 요청 분석 후 실제 수정 대상과 참조 대상을 명세로 확인한다
시작점을 바꿔도 권한·허용 경로·검증 조건은 달라지지 않는다
최초 권장 구현은 하나의 조정 흐름으로 순차 수정하고, 필요 서비스들만 동시에 기동한다. 프로젝트마다 독립 에이전트를 만드는 것은 필수가 아니다

### 예: 목록 화면에 고객 등급 추가

1. 매니저가 `고객 서비스`에서 “고객 목록에 등급을 표시해 주세요”라고 요청
2. AI가 API 응답, 프론트엔드 표시, 타입 정의, 권한별 노출, 기존 고객 데이터 처리 여부 확인
3. 등급의 출처·표시 규칙 등 누락된 내용은 질문하고, 영향받는 엔드포인트·함수·화면·데이터를 프로젝트별로 정리
4. backend와 frontend 수정, contracts 참조 등 대상·제외 범위·성공 조건을 사용자에게 확인
5. 각 대상의 고정된 기준 코드로 작업 사본 생성, 개별 검사와 연동 검사 수행
6. “어디가 바뀌었고 무엇을 확인했는지” 통합 보고, 매니저가 재수정 요청 또는 결과 확인
7. 관리자가 동일한 통합 결과를 승인. 승인만으로 push·PR·배포하지 않음

기존 `(사용자) 요청 → 분석·보완 → 명세 확인 → 수정·검증 → 결과 확인/재수정 → 관리자 승인` 흐름을 유지한다

## 4. 관리자 입력과 매니저 화면

### 프로젝트 추가·그룹 구성

- 기존 단일 프로젝트 추가 방식 유지, `여러 프로젝트 연결` 선택 시 그룹 이름과 구성원 입력
- 기존 프로젝트 선택 또는 새 저장소 등록, 프로젝트별 Path·Branch·정책·준비 상태 확인
- 같은 저장소를 새 Project로 중복 등록하지 않고 기존 항목을 재사용
- 메인은 복수 선택, 분석 시작점은 선택 사항, 목록 순서를 실행 순서로 해석하지 않음
- 연결 저장은 코드 수정이나 서비스 기동이 아님
- 먼저 모든 입력을 검증하고 제출 확인 모달에서 그룹·대상·새 브랜치 생성 예정 사항을 요약
- 여러 저장소의 브랜치 생성 등 Git 작업은 DB 트랜잭션으로 되돌릴 수 없으므로 대상별 처리 결과 기록. 일부 실패 시 재시도할 대상을 표시하고 전체 완료로 표시하지 않음

### 매니저

- 할당된 업무 대상 선택, 요청·기대 결과·필요 자료 입력
- 확정 전 수정할 프로젝트·참조만 할 프로젝트·확인할 결과를 쉬운 이름으로 표시
- 작업 중 대상별 `대기/분석/수정/검증/완료/실패`와 전체 상태 표시
- 결과는 사용자 관점 요약 우선, 프로젝트별 변경 내역·검증 증거는 펼쳐서 확인
- 긴 경로·CLI·환경변수·내부 식별자는 기본 화면에서 숨김
- 모바일은 프로젝트별 묶음, PC는 상태 표 사용. 기존 헤더·고정 높이 네비·노티·본문·푸터 정렬 기준 유지

## 5. 권한과 설정

### 권한 — 계정과 프로젝트 기준 유지

- ADMIN만 그룹·프로젝트 연결·정책·환경·계정 할당을 관리하고 결과를 승인
- MANAGER는 요청 대상 모두에 기존 ProjectMembership이 있어야 하며 요청 소유자 조건도 충족해야 함
- 초기 권장안은 별도 그룹 권한 체계를 중복 추가하지 않고 구성 프로젝트 권한으로 그룹 접근을 계산
- 일부 구성원 권한이 없는 그룹은 최초 버전에서 사용 불가. 단일 프로젝트 사용은 별개이며, 숨겨진 이름·경로·결과가 오류나 AI 답변에 노출되지 않도록 처리
- 연결 자체로 권한을 상속하지 않음. 일괄 할당 UI를 추가한다면 관리자가 대상별 권한 변경을 확인하는 별도 동작
- 대화 문맥 수집, 제출, worker 시작, 결과 조회·다운로드, 승인 시 권한 재검사
- 실행 중 권한 회수는 새 단계 중지·조회 차단·취소 처리에 반영. 이미 실행한 명령이나 외부 전달 자료가 되돌아갔다고 표시하지 않음
- AI가 다른 프로젝트 수정 필요성을 발견하면 명세 보완으로 돌아감. 대상이나 읽기 범위를 임의 확대하지 않음

### 설정 — 종류별로 합성 방식 구분

아래는 새 기능에 필요한 제안이며, 현재 앱에 전역·그룹 설정 화면이 이미 있다는 의미가 아니다

| 설정 | 관리 위치 | 적용 방식 |
| --- | --- | --- |
| 분석·수정 모델과 effort | 기존 AI 설정 | 목적별 명시, 지원 실패 시 다른 모델로 자동 교체하지 않음 |
| 공통 작업 지침·보고 양식 | 전역 기본값 후보 | 그룹·프로젝트 지침과 출처를 함께 기록, 충돌 시 확인 |
| API 관계·공동 성공 조건 | 그룹 | 프로젝트 개별 조건에 추가, 기존 필수 검증을 제거하지 않음 |
| 읽기·쓰기 범위 | 프로젝트 정책 + 그룹 참여 한도 + 요청 범위 | 교집합 적용, 참조 전용은 수정 불가 |
| 이미지·런타임·준비/검사 명령·cwd | 프로젝트 | Python/Node 등 서로 다른 환경 유지 |
| 서비스 연결·healthcheck·공동 E2E | 그룹 실행 환경 | 프로젝트별 서비스에 명시적으로 연결 |
| 환경변수 | 서비스별 값 + 선택한 공통 값 | 같은 키 충돌은 명시적으로 해결, 모든 값 자동 공유 금지 |
| 비밀 값 | 관리자 지정 실행 환경 참조 | 모델 문맥·일반 결과에 원문 저장하지 않음, 필요한 서비스에만 전달 |

AGENTS.md·프로젝트 규칙의 적용 범위는 해당 프로젝트다. 그룹 전체 변경을 요구하거나 서로 충돌하는 지침은 분석 단계에서 알려준다
호스트의 전체 환경변수나 임의의 `.env`를 묶음 전체에 자동 전달하지 않는다
그룹 설정 버전과 프로젝트별 버전, 실제 적용 값/출처를 명세·실행에 고정한다. 비밀 값 대신 참조와 버전을 기록한다

## 6. 실행·Git·Docker 설계 검토

### 코드와 이력

- 요청 대상마다 project_id, 기준 브랜치와 해석된 SHA, 정책 버전, 읽기/수정 범위, 대상 역할을 고정
- 원본 저장소의 현재 checkout·staged·unstaged·untracked를 작업 입력에 섞거나 변경하지 않음
- 현재의 **허용 파일 투영 → 독립 저장소 → 작업 worktree** 방식을 대상별로 확장. 원본 저장소에 직접 연결된 worktree로 몰래 바꾸지 않음
- 각 저장소의 결과 브랜치·커밋·검증 증거를 개별 기록하고 공통 요청 ID로 연결
- 저장소별 브랜치명·커밋 메시지 규칙 검사. 하나의 저장소만 커밋되면 부분 결과이지 전체 완료가 아님
- 결과 브랜치가 앱 작업 저장소에 있는지 원본 저장소로 명시적 반영됐는지 화면에서 구분. GitHub Desktop에서 볼 수 있다고 자동 가정하지 않음
- 같은 Git 저장소의 backend/frontend 하위 폴더는 별도 저장소 두 개가 아니다. 한 작업 사본에서 범위·검증 명령을 나눔
- 별칭 중복, 동일 canonical 경로 중복, 중첩 저장소·submodule·심볼릭 링크는 등록 단계에서 판별. 초기 버전의 별도 지원 범위는 Q3에서 결정

### 실행 환경

- 여러 프로젝트의 부모 폴더 전체가 아닌 확정된 사본만 마운트
- `대상 별칭 + 상대 경로`로 파일·명령 위치를 지정해 서로 다른 `src/index.ts`가 섞이지 않도록 처리
- 분석은 허용된 모든 대상의 읽기 문맥을 사용하되 수정 단계의 파일 접근은 대상별 정책으로 제한
- 쓰기 마운트는 수정 대상, 참조 대상은 읽기 전용. 런타임 쓰기가 필요한 캐시·생성물은 별도 작업 영역 사용
- 외부 네트워크는 허용 유지. 패키지 설치·외부 문서·API 접근 때문에 일괄 차단하지 않음
- 앱의 기존 worker가 컨테이너 생명주기를 관리, 모델 컨테이너에 Docker 소켓이나 호스트 홈을 넘기지 않음
- 서비스별 이미지·명령·기동 순서·준비 완료 기준·timeout·포트·테스트 데이터 정의 필요
- Docker Compose는 공동 실행 환경의 후보이지 확정 의존성은 아님. 저장소의 Compose 파일을 검토 없이 그대로 실행하지 않음
- 실행 ID별 네트워크·볼륨·컨테이너 이름을 사용. 호스트 preview 포트는 충돌 검사하고 자동 배정된 실제 URL 표시
- 컨테이너 내부 API 주소와 호스트 브라우저 API 주소를 구분. 서비스 이름 주소를 사용자 브라우저에 그대로 전달하지 않음
- 테스트 DB는 실행 전용 데이터 사용, 운영 DB·호스트 개발 DB를 암묵적으로 재사용하지 않음
- 첫 구현은 기존 전역 실행 슬롯 하나에서 요청 전체를 처리. 여러 서비스 기동과 여러 요청 병렬 처리를 혼동하지 않음

### 검증과 결과

- baseline 조합 `backend@A + frontend@B`와 후보 조합 `backend@A' + frontend@B'`를 기록
- 개별 테스트뿐 아니라 API 계약·생성 타입·공동 화면 등 명세의 연동 성공 조건을 검사
- 대상별 소스와 연동 환경을 고정한 뒤 검사. 검사 중 소스 변경은 실패이며 같은 코드였다고 간주하지 않음
- 모든 필수 개별/연동 검증과 결과 봉인이 완료돼야 전체 성공
- 한 대상 실패·서비스 준비 실패·검사 누락 시 성공한 대상의 증거는 보존하되 통합 승인 불가
- 재시도는 새 실행·사본·컨테이너. 실패 사본을 이어 쓰거나 성공한 한쪽만 바꿔 검증 조합을 섞지 않음
- 종료가 불확실한 로컬 실행은 ABANDONED로 기록하고 환경을 분리해 새 실행 허용. 이전 결과를 새 실행 결과에 포함하지 않음
- 취소·정리는 실행 소유 리소스만 대상으로 수행, 다른 요청·개발 환경·원본 코드를 삭제하지 않음

## 7. 결과 확인·승인·발행

통합 결과는 대상별 baseline SHA·후보 tree hash·커밋·개별 검사와 연동 검사, 명세 hash를 포함한다
사용자 확인과 관리자 로컬 승인은 이 통합 결과 hash에 연결한다. 어느 한쪽을 재수정하면 새 결과를 만들고 다시 확인한다

멀티 프로젝트의 원격 발행은 최초 구현에서 제외하는 것을 권장한다. 단일 프로젝트의 기존 발행 기능을 임의 제거한다는 뜻은 아니다
후속 지원 시에도 프로젝트별 원격 대상·정책·자격 증명과 별도 발행 승인이 필요하다
여러 저장소 push를 하나의 원자적 작업으로 취급할 수 없으므로 부분 발행·중복 방지·상태 대조를 설계해야 한다
부분 발행을 되돌리려고 자동 force-push·원격 브랜치 삭제를 수행하지 않는다. 근거는 [Git 조사](research.md)에 있다

## 8. 구현 전 결정할 질문

지금 답해야 하는 차단 질문이 아니라, 구현 착수 전에 확인할 목록이다. 모두 **미확정**이다
복수 메인 지원 자체는 사용자 요구이므로 단일 메인으로 제한하는 선택지는 두지 않는다

## 9. 구현 순서와 완료 기준

모든 항목은 미구현이다. 단계별 코드를 작성하기 전에 현재 도메인 계약을 갱신하고 수용 테스트를 확정한다

1. **계약·데이터**: 질문 확정, 그룹/구성원/명세 대상/실행 대상/통합 결과의 책임 설계, 기존 단일 요청·이력·URL 호환 및 마이그레이션 계획
2. **등록·조회**: 관리자 다중 연결·준비 상태·멤버십 판정, 매니저 업무 대상 선택을 DB부터 화면까지 연결
3. **분석·확인**: 공동 문맥·질문·영향 분석·대상별 불변 명세, 대상 변경 시 재확인
4. **로컬 실행**: 대상별 사본·브랜치·커밋, Docker 환경·개별/연동 검사, 실패·취소·재시도 기록
5. **결과·승인**: 통합 결과 보고 → 사용자 재수정/확인 → 관리자 로컬 승인, 실제 브라우저 흐름 검증
6. **선택적 확장**: 모듈 등록·병렬 수정·여러 저장소 발행은 별도 결정 후 진행

### 수용 테스트 목록

- [ ] backend/frontend 둘 다 메인으로 저장·재조회, 시작점 미지정 허용
- [ ] 프론트엔드만 수정하고 backend는 참조하면 backend 결과 소스 불변
- [ ] API와 UI 동시 변경 시 영향 분석·명세·각 diff·개별/연동 검사 모두 표시
- [ ] 없는 브랜치 생성 시 저장소별 규칙 검증, 한쪽 실패 후 중복 생성 없는 재시도
- [ ] 동일 저장소 중복·별칭 충돌·잘못된 경로·중첩 구성은 정확한 입력 오류로 반환
- [ ] 한 프로젝트 권한 누락·회수 시 직접 URL/API/첨부·로그 다운로드와 AI 문맥 모두 차단
- [ ] 두 원본 저장소의 HEAD·index·dirty·untracked 보존, 결과 커밋의 저장 위치 확인
- [ ] 요청 확정 후 대상·브랜치 기준·정책 변경 시 기존 실행 입력이 조용히 바뀌지 않음
- [ ] Python/Node 서로 다른 환경에서 API 기동 → 준비 확인 → UI E2E 수행
- [ ] 포트 충돌·DB 기동 실패·환경변수 누락·순환 실행 의존성에 원인과 복구 안내 표시
- [ ] 한쪽 검사 실패·건너뜀·결과 커밋 실패 시 전체 성공·승인으로 진행하지 않음
- [ ] 취소·worker 재시작·종료 미확인 이후 새 실행이 이전 리소스나 결과를 재사용하지 않음
- [ ] 재수정으로 후보가 바뀌면 이전 사용자 확인·관리자 승인이 새 결과에 적용되지 않음
- [ ] 매니저 로그인 → 공동 요청 → 보완 질문 → 명세 확인 → 실행 → 결과 확인 → 관리자 승인 E2E
- [ ] 모바일·패드·PC에서 대상별 상태·입력 오류·확인 모달·결과 목록 확인
- [ ] 기존 단일 프로젝트 등록·요청·결과·승인·기록 조회 회귀 테스트 통과
- [ ] 최초 멀티 프로젝트 검증 중 원격 push·PR 호출 0회 확인
