# 승인과 발행

이 문서는 로컬 Django 앱의 승인·선택적 GitHub 발행 계약이다. 실제 GitHub 발행은 미검증이며 테스트 중 원격 push는 금지한다. [현재 검증 기록](../operations/verification.md)을 따른다.
발행은 선택 기능이다. 관리자가 설정하지 않아도 코드 수정 결과와 패치를 로컬에서 확인할 수 있어야 한다.

`Admin / Approvals`에는 사용자가 완료 확인한 로컬 결과를 먼저 표시한다. `로컬 결과 승인`은 [ResultReview](../artifacts/README.md)에만 기록하며 push·PR을 실행하지 않는다. 사용자는 결과 확인 또는 재수정을 선택하고, 관리자는 그 뒤에 승인 또는 보완을 요청한다. 아래 Publication/Approval 계약은 **그 이후 별도로 선택하는 원격 발행**에만 적용한다. 로컬 승인만으로 원격 발행 동의를 추론하지 않는다.

## 1. 목적과 도메인 소유권

매니저의 업무 요청을 원격 저장소에 반영할지는 관리자 앱 계정이 결정한다. 코드 수정 실행, 결과 검토, 발행 승인은 서로 다른 행위다.

| 이 도메인이 소유 | 다른 도메인에서 참조 |
| --- | --- |
| `PublicationPolicy`: 허용 저장소·기준 브랜치·발행 모드 | [프로젝트](../projects/README.md)의 ID와 `project_config_version` |
| `Publication`: 특정 결과 한 건의 발행 상태와 대상 스냅샷 | [실행](../runs/README.md)의 상태와 기준 커밋 |
| `Approval`: 누가 어떤 발행을 승인·거절했는지 | [계정](../accounts/README.md)의 현재 역할·활성 여부 |
| `PublicationAttempt`: 원격 작업 단계와 복구 증거 | [결과물](../artifacts/README.md)의 불변 `ResultBundle` |

계정 역할이나 결과 파일을 이 도메인에 복제하지 않는다. 승인 당시 식별자·버전·해시만 고정한다.
작업 처리는 같은 Django 프로젝트의 작업 프로세스를 사용하며, 별도 발행 서버나 내부 HTTP 서비스는 만들지 않는다.

## 2. 계정별 권한

| 행위 | 매니저 `MANAGER` | 관리자 `ADMIN` |
| --- | --- | --- |
| 자기 요청의 결과·발행 상태 확인 | 프로젝트 접근 권한이 있는 동안 허용 | 모든 프로젝트 허용 |
| 발행 대상·모드 설정 | 거부 | 허용 |
| 발행 승인·거절 | 거부 | 허용 |
| push·Draft PR 생성·실패 복구 요청 | 거부 | 승인된 범위만 허용 |
| 원본 브랜치 push·기존 원격 브랜치 덮어쓰기·merge·배포 | 거부 | 앱 기능으로 제공하지 않음 |

- 서버 실행자라는 사실, OS 계정, localhost, 접속 IP, 휴대폰 여부는 앱 관리자 권한의 근거가 아니다.
- `is_staff`나 버튼 노출 여부만 검사하지 않는다. 서버가 로그인 계정의 활성 여부·`ADMIN` 역할·대상 프로젝트를 확인한다.
- 관리자 역시 결과의 무결성·필수 검증·허용 대상을 우회할 수 없다. 본인이 요청한 결과를 승인하는 것은 허용한다.
- 매니저가 URL·ID·폼 데이터를 바꾸거나 Codex에 push를 요청해도 승인·작업 생성·원격 변경이 발생하지 않는다.
- Codex의 요약·검토 성공은 사람의 승인 기록을 만들지 않는다. 채팅의 “승인”, “진행”도 발행 동작을 호출하지 않는다.

## 3. 운영 기본값과 설정

기본값은 `PublicationPolicy.enabled=false`다. 관리자가 아래 정보를 등록하고 사전 검사를 통과한 프로젝트만 발행 버튼을 제공한다.

| 필드 | 기본값·검증 |
| --- | --- |
| `project_id`, `version`, `enabled` | 프로젝트당 활성 정책 하나. 발행 설정 변경은 이 version만 증가; `project_config_version`은 실행 입력·검증 설정에만 사용 |
| `repository_host`, `repository_id`, `repository_full_name` | 최초 지원은 `github.com`. 기존 저장소를 읽어 ID와 `owner/repo`를 확인 |
| `remote_url` | 위 저장소와 일치하는 자격증명 없는 HTTPS URL. 임의 프로토콜·URL 내 토큰·리다이렉트 대상 불일치 거부 |
| `base_branch` | 관리자가 지정한 기존 브랜치. 원본의 기준 커밋과 원격 기준 SHA가 같아야 발행 가능 |
| `mode` | `PUSH` 또는 `PUSH_AND_PR`. 활성화 시 기본 `PUSH_AND_PR` |
| `commit_author_name`, `commit_author_email` | 관리자가 확인한 Git 작성자 정보. 매니저 입력이나 Git 전역값을 자동 채택하지 않음 |

`PUSH`는 앱이 만든 새 원격 브랜치까지만, `PUSH_AND_PR`은 같은 브랜치에 GitHub Draft PR까지 생성한다.
생성 브랜치는 `aiqa/run-<run_uuid>`로 고정한다. 매니저·모델이 이름·refspec·원격 URL을 입력하지 않는다.
원격 저장소를 자동 생성하거나 저장소 권한을 바꾸지 않는다. 정책 비활성화는 로컬 결과를 삭제하지 않는다.
운영자가 기존 호스트의 Git 인증·`gh` 로그인을 준비한다. 앱은 토큰을 DB·브라우저·채팅에 복사하거나 로그인 화면을 대신 수행하지 않는다.
정책 화면은 연결 상태·GitHub 계정 표시명·권한 검사 결과만 보여주고 자격증명 값은 출력하지 않는다.

발행 정책의 최초 활성화는 이전 로컬 결과를 무효화하지 않는다. 새 Publication이 현재 발행 정책 version을 고정하고 관리자가 그 대상을 승인한다. 정책 변경은 기존 미완료 승인을 무효화하며 자동 승인 승계는 없다. 해당 프로젝트의 발행 준비/실행 중에는 정책 변경을 `PROJECT_BUSY`로 거부하고, 중단·원격 대조가 끝난 뒤 변경한다.

## 4. 발행 가능 조건

다음 조건을 모두 만족해야 `PENDING_APPROVAL`을 만들 수 있으며, 승인할 때와 실제 발행 직전 다시 확인한다.

현재 승인 POST는 로컬 계정·정책·결과를 재검사하고 worker가 저장한 마지막 원격 관측에 결속한다. HTTP 안에서 원격 CLI를 기다리지 않으므로 승인 시각의 원격 SHA를 새로 조회한 것과 같지는 않다. 관측 시각을 표시하고 실제 worker는 원격 쓰기 직전/직후 다시 조회한다. 승인 순간부터 원격 base를 잠갔다고 표시하지 않는다.

1. 계정과 프로젝트가 활성 상태이고 해당 프로젝트의 현재 관리자 권한이 있다. 아카이브된 프로젝트도 과거 결과 조회·원격 읽기 대조는 허용하지만 새 준비·승인·원격 쓰기는 거부한다.
2. 실행 상태가 `SUCCEEDED`이며, 관리자 등록 필수 검증이 한 개 이상이고 모두 `PASS`다.
3. 설정 없음·미수행·타임아웃·알 수 없는 검증은 통과가 아니다. 테스트 건수 등 증거 기준은 실행 도메인을 따른다.
4. `ResultBundle`이 완전하고 비밀 탐지·범위 위반·필수 파일 누락·해시 불일치가 없으며, 승인 이후 덮어쓰지 않았다. manifest에 명시된 보조 로그의 정상 만료는 artifacts의 만료 증거로 확인하며 필수 증거 유실과 구분한다.
5. 정책이 활성 상태이고 결과 생성 시점의 `project_config_version`이 현재 설정과 일치한다.
6. 원격 저장소 ID·이름·호스트·기준 브랜치가 승인 화면의 대상과 일치한다.
7. 원격 기준 브랜치의 SHA가 `ResultBundle.baseline_commit_sha`와 같다. 원본의 미발행 커밋까지 함께 전송하지 않는다.
8. [AI 실행 보호 검사](../ai/README.md)를 통과하여 Codex·대상 코드에서 발행 자격증명과 발행 실행 경로에 접근할 수 없음이 확인되었다.

기준 SHA가 바뀌면 자동 rebase·cherry-pick하지 않는다. 기존 결과는 로컬에서 보존하고 올바른 기준으로 새 요청 버전과 실행을 만든다.
발행하지 않는 선택은 실패가 아니다. `SUCCEEDED`와 “원격 미발행”을 함께 표시할 수 있다.

## 5. 데이터와 불변 조건

| 모델 | 필수 데이터와 제약 |
| --- | --- |
| `Publication` | UUID, project/run ID, 상태, 모드, 결과 묶음 ID·version·manifest SHA-256, baseline SHA, `project_config_version`, 정책 ID·version, 저장소 ID·이름·URL, 기준 브랜치·SHA, 생성 브랜치, 승인한 commit SHA, 생성·갱신 시각, 남은 단계 포기 시 actor·시각·사유 |
| `Approval` | UUID, publication ID, 실제 actor user ID, `APPROVE`/`REJECT` 결정, 대상 스냅샷 해시, 사유, 결정 시각, 유효 여부·무효 사유. 결정 내용은 덮어쓰지 않음 |
| `PublicationAttempt` | UUID, publication/approval ID, 시도 번호, 작업 ID, 단계, 시작·종료 시각, 단계별 요청/확인 commit SHA, branch·PR 번호·URL, 오류 분류, 민감값 제거된 확인 증거 |

- 대상 스냅샷 해시는 정규 직렬화한 모든 승인 필드에서 계산한다. 결과 해시만 같고 대상 저장소가 다른 승인은 재사용할 수 없다.
- 결과의 기준 트리와 canonical patch를 이용해 신뢰된 발행 모듈이 커밋을 조립하고 SHA를 확정한 뒤 승인 화면을 표시한다. 이 준비도 HTTP가 아닌 worker의 실행 슬롯에서 처리한다.
- 원본 baseline SHA의 parent 객체는 tree 파일만으로 만들 수 없다. 신뢰된 발행 모듈이 새 Git 저장소에서 고정 HTTPS 원격의 기준 ref를 tags·재귀 없이 fetch하고, FETCH_HEAD가 baseline SHA와 같은지 검사해 원본 commit 객체를 독립 확보한다. 보존 baseline tree와 원격 tree도 대조한다. 원본 로컬 repo나 Codex 사본의 Git object는 공유하지 않는다. 이 읽기 전용 원격 준비는 push·PR 생성이 아니다.
- 커밋의 parent는 고정 baseline SHA 하나다. 작성자·메시지·시간·트리도 고정하여 재시도 중 다른 SHA가 만들어지지 않게 한다.
- 동일 Run의 생성 브랜치는 하나다. 발행 성공 후 같은 Run을 다른 대상·모드로 다시 발행하지 않는다.
- 결과·원본 SHA·실행 설정·발행 정책 version·대상·모드가 바뀌면 기존 승인은 무효다. 이전 결정은 감사 이력으로 남긴다. 실행 설정이 같다면 새 발행 정책에 대한 재검토·승인에 기존 로컬 결과를 사용할 수 있다.
- 무효화 시 이미 발생한 원격 변경은 지워지지 않는다. `PARTIAL`·`PUBLISHED` 기록을 “아무 일도 없었던 실패”로 바꾸지 않는다.
- 원격 credential은 모델 필드가 아니다. 발행 전후 감사 로그에는 계정·결과·대상·동작·시각·관측 결과만 남긴다.

## 6. 관리자 화면과 승인 트랜잭션

관리자는 결과 상세에서 요청 요약, 변경 파일과 전체 diff 접근 경로, 실제 검증·미수행 항목, 기준 SHA, 생성 commit SHA를 확인한다.
발행 카드에는 GitHub 저장소, 기준 브랜치, 새 브랜치, 실행 모드, 외부로 전송되는 정보와 원격 CI가 실행될 수 있음을 표시한다.
버튼은 `승인 후 발행`, `발행 거절`이다. 승인과 발행을 분리된 무맥락 버튼 두 개로 제공하지 않는다.
PR 제목·본문은 요청 제목·결과 요약·검증표·실행 ID로 서버가 구성하며, 비밀·로컬 절대경로·원문 로그를 넣지 않는다.

`승인 후 발행` POST는 Django 세션·CSRF를 검증하고 다음을 단일 DB 트랜잭션으로 처리한다.

1. 계정·정책·Publication의 현재 상태/버전을 확인하고 경합 시 조건부 갱신으로 한 요청만 승인한다.
2. 클라이언트의 대상값을 신뢰하지 않고 DB의 스냅샷 해시와 현재 결과·권한을 대조한다.
3. 실제 로그인 계정에 결속된 `Approval`을 기록하고 `APPROVED`로 변경한다.
4. 동일 트랜잭션에서 `publication_id`를 참조하는 영속 Job을 하나 등록한다. 커밋 이전에는 실행하지 않는다.

승인 요청의 idempotency key는 계정·Publication·스냅샷에 결속한다. 같은 요청 재전송은 같은 결과를 반환한다.
다른 payload에 같은 key를 쓰거나 두 관리자가 상반된 결정을 경합하면 `409`와 현재 결정을 반환한다.
승인됐지만 Job이 없는 상태, Job은 있지만 승인이 없는 상태가 DB에 커밋되지 않아야 한다.
거절은 `REJECTED`로 남기며 원격 작업을 만들지 않는다. 수정 요청은 기존 승인 내용을 바꾸지 않고 새 실행으로 이어진다.

## 7. 발행 상태

Run 상태와 아래 Publication 상태를 별도로 저장한다. 승인 대기는 코드 실행 슬롯을 점유하지 않는다.

| 상태 | 의미·허용되는 다음 동작 |
| --- | --- |
| `PENDING_APPROVAL` | 관리자의 결정 대기. 승인 또는 거절 |
| `APPROVED` | 승인·작업 등록 완료, 실제 원격 작업 전. 작업 직전 재검증 또는 무효화 |
| `PUBLISHING` | 작업자가 실행 슬롯을 확보하고 단계별 발행 중 |
| `PUBLISHED` | 정확한 branch/commit과 모드에 따른 Draft PR을 확인하고, 마지막 대조에서 base·권한·승인 조건도 충족 |
| `REJECTED` | 관리자 거절. 로컬 결과는 유지 |
| `INVALIDATED` | 원격 변경 전 승인 조건이 달라짐. 같은 승인으로 실행 불가 |
| `FAILED` | 해당 시도에 원격 변경이 없음을 확인한 실패. 원인 해결 후 명시적 복구만 허용 |
| `UNKNOWN` | 타임아웃·프로세스 중단 등으로 원격 반영 여부를 모름. 자동 재시도 금지 |
| `PARTIAL` | 원격 변경은 확인됐지만 승인한 전체 완료 조건은 미충족. PR 미완료 또는 생성 후 base·권한 변경 등을 포함하며 실제 branch/PR을 보존하고 추가 쓰기를 중단 |

기본 전이는 `PENDING_APPROVAL → APPROVED → PUBLISHING → PUBLISHED`다.
정책·권한 변화는 원격 변경 전에는 `INVALIDATED`, 일부 변경 후에는 `PARTIAL`과 승인 무효 사유를 함께 기록한다.
취소는 아직 원격 작업을 시작하지 않은 승인만 무효화할 수 있다. 실행 중 취소를 원격 rollback으로 표현하지 않는다.

### 내부 Interface와 웹 입력

| Interface | 입력·출력·호출자 |
| --- | --- |
| `prepare_publication(actor, run_id, idempotency_key)` | 관리자만 호출. 멱등 준비 Job을 반환하고 worker가 원격 기준 읽기·로컬 commit 조립 후 `PENDING_APPROVAL` 생성. HTTP에서 CLI 대기 없음, 원격 변경 없음 |
| `decide_publication(actor, publication_id, snapshot_hash, decision, idempotency_key)` | 관리자 POST의 진입점. 승인/거절·Job 등록을 결속하고 현재 상태 반환 |
| `execute_publication(job_id)` | 내부 작업자 전용. Job→승인→불변 대상 순서로 확인. 임의 URL·명령을 인자로 받지 않음 |
| `reconcile_publication(actor, publication_id)` | 관리자 요청으로 읽기 전용 대조 Job 등록. worker가 원격 사실만 조회하고 별도 명시적 복구 POST 전에는 원격 쓰기 없음 |
| `approve_remaining(actor, publication_id, snapshot_hash, idempotency_key)` | 원격 대조 완료된 PARTIAL에 대해 활성 관리자가 동일 결과·commit/ref·대상·정책의 남은 PR 단계만 새 Approval로 승인. 이전 승인과 관측 기록 보존, 재push 없음 |
| `abandon_remaining(actor, publication_id, snapshot_hash, reason, idempotency_key)` | 원격 사실·프로세스 종료가 확인된 미완료 발행만 ADMIN이 명시적으로 포기. 상태·원격 결과는 보존하고 추가 Job 등록 금지·pin 해제; UNKNOWN인 동안은 거부 |

폼에는 Publication ID·스냅샷 해시·결정·중복방지 키·선택 사유만 받는다. actor·Git 명령·대상 URL을 받지 않는다.
비로그인은 로그인 안내/`401`, 권한 부족은 `403`, 접근 불가 객체는 `404`, 오래된 스냅샷·상태 경합은 `409`로 처리한다.
실패 응답에 Git 자격증명·원본 경로·다른 사용자의 결과를 포함하지 않는다. GET 요청은 승인·Job 생성·원격 변경을 일으키지 않는다.

## 8. 신뢰된 발행 실행

발행 Job도 [실행](../runs/README.md)의 앱 전체 실행 슬롯 한 개를 공유한다. 코드 수정·검증·발행이 겹치지 않게 한다.
작업자는 승인 ID로 원본 기록을 읽고 계정 활성·역할·결과 해시·정책 버전·원격 대상·기준 SHA를 다시 검사한다.
불변 자료를 읽는 것 외에 Codex workspace나 원본 저장소에서 명령을 실행하지 않는다.

1. 준비 때 독립 확보한 baseline commit과 보존된 baseline 자료·canonical patch를 별도 발행 사본에 조립한다. 원격 기준 SHA를 재조회하고 결과 tree hash와 승인 commit SHA를 대조한다. 준비 자료가 사라졌으면 고정 원격에서 다시 읽되 승인 SHA를 바꾸지 않는다.
2. 새로 초기화한 Git 저장소에만 접근한다. 작업 저장소의 `.git/config`, hooks, attributes 기반 실행 설정, credential helper를 가져오지 않는다.
3. 파일은 데이터로 처리한다. build/test·프로젝트 스크립트·Git hook·필터·서브모듈·사용자 지정 signer를 발행 과정에서 실행하지 않는다.
4. Git 명령은 승인된 실행 파일과 고정 argv로 호출한다. 원격 URL·refspec을 shell 문자열로 조립하지 않는다.
5. Git 전역 include·URL rewrite·추가 push URL·push tags·submodule 재귀 등을 상속하지 않는다. 관리자 검증된 호스트 인증 경로만 별도 허용한다.
6. 생성할 ref의 부재를 확인하고, 실제 push에서도 “존재하지 않을 때만 생성” 조건을 적용한다.
7. push 후 정확한 저장소·ref의 SHA와 base·권한·승인 조건을 다시 확인한다. `PUSH`는 이 최종 대조까지 충족한 뒤 `PUBLISHED`다.
8. `PUSH_AND_PR`은 base SHA와 권한·승인 조건을 다시 확인한 뒤 같은 저장소·head branch·base branch로 Draft PR을 생성한다. 번호·URL·head SHA·관측한 base SHA와 현재 권한·승인 조건을 최종 대조한 뒤 `PUBLISHED`로 기록한다.

각 원격 변경 직전 짧은 DB 트랜잭션으로 현재 승인·권한·정책을 재검사하고 `PublicationAttempt`에 dispatch 대상을 기록한다. 그 뒤 네트워크를 호출하며 transaction을 유지하지 않는다. 권한 회수는 이후 단계를 차단하지만 이미 발송한 요청을 없던 일로 만들 수는 없으므로, 진행 중이던 요청은 원격 대조로 실제 결과를 판정한다.

새 branch에 대한 조건부 생성은 base branch까지 잠그는 동작이 아니다. base SHA는 준비·승인·push 직전, push 직후, PR 직전과 최종 대조에서 관측한다. 원격 변경 전 불일치는 INVALIDATED, branch 또는 PR 생성 후 불일치는 PARTIAL과 실제 생성된 객체를 기록하고 추가 쓰기를 중단한다. 최종 대조 이후 다른 사람이 base를 변경하는 것까지 막았다고 보장하지 않으며 마지막 관측 시각·SHA를 남긴다. 자동 rebase·기존 ref 수정은 없다.

신규 ref의 원자적 생성에는 `--force-with-lease=refs/heads/<generated-branch>:`만 허용한다. 마지막 기대값은 반드시 빈 문자열이다.
이는 기존 ref 덮어쓰기가 아니라 **원격 ref가 없을 때만 생성하는 조건부 동작**이다. 사전 조회와 push 사이 경합도 거부해야 한다.
일반 `--force`, `+refspec`, 기대 SHA가 있는 lease, 기대값 없는 lease, 복수 ref·태그·삭제 push는 허용하지 않는다.
이 규칙은 Git의 [명시적 기대값을 사용하는 push 계약](https://git-scm.com/docs/git-push)을 근거로 하며, 구현 시 임시 저장소의 동시 생성 테스트로 확인한다.

PR 생성은 기존 호스트 로그인으로 `gh`를 호출하고 저장소·head·base·draft를 명시한다. 이미 같은 발행의 PR이 있으면 재생성하지 않는다.
PR은 리뷰 요청 결과일 뿐 merge·배포 승인이 아니다. 자동 merge, ready 전환, 리뷰어 지정, 원격 브랜치 정리는 제공하지 않는다.

## 9. 자격증명 보호와 선행 검사

Codex·대상 프로젝트 코드·검사 명령은 Docker 컨테이너에서 실행한다. 해당 작업 사본과 Codex 로그인에 필요한 파일만 제공하며 호스트 Git/gh 인증·SSH agent·Docker 소켓·DB는 마운트하지 않는다. 네트워크는 허용하므로 신뢰하는 프로젝트만 연결한다. Codex 로그인 파일은 모델 호출 컨테이너 안에서 접근 가능하며, 모든 컨테이너 내부 비밀을 코드로부터 격리한다고 주장하지 않는다. 상세 경계는 [AI](../ai/README.md)를 따른다.

원격 발행은 별도 관리자 승인 서비스가 수행한다. 이전 로컬 작업의 종료가 불명확하면 새 작업을 시작할 수 있지만, 이미 전송한 push·PR의 결과가 불명확할 때에는 원격 대조 없이 같은 발행을 반복하지 않는다.
인증된 브라우저 세션·CSRF 값·발행 Job/DB·보존 결과·관리자 설정은 Codex 및 대상 코드의 접근 가능 자료에서 제외한다.

## 10. 오류와 복구

| 상황 | 기록·운영 대응 |
| --- | --- |
| Git/gh 로그인 만료·쓰기 권한 없음 | 원격 변경이 없음을 확인했으면 `FAILED`, branch 생성 확인 뒤면 `PARTIAL`, 반영 여부 불명이면 `UNKNOWN`. 관리자가 터미널에서 해결하며 자동 로그인·권한 확대 없음 |
| 결과·대상·권한·정책 변경 | 원격 변경 전 `INVALIDATED`. 결과 재검토·새 승인 없이 실행 금지 |
| 생성 ref가 이미 있음 | 임의 push 금지. 동일 Publication의 승인 commit이면 증거로 복구, 다르면 충돌로 중단 |
| push 타임아웃·작업자 종료 | `UNKNOWN`. 정확한 branch/commit 조회로 반영 여부부터 판별 |
| push 확인 후 PR 생성 실패 | `PARTIAL`. branch/commit 링크를 보여주고 PR 단계만 명시적 복구 |
| PR 생성 응답 유실 | `UNKNOWN`. 동일 저장소·head·base의 PR과 head SHA를 조회. 확인되지 않으면 생성 반복 금지 |
| 승인자는 비활성화됐지만 branch는 이미 생성됨 | `PARTIAL` 유지·추가 동작 중단. 실제 원격 결과를 숨기거나 자동 삭제하지 않음 |

복구 버튼은 관리자에게만 보이며 현재 원격 상태의 읽기 전용 확인과 그 증거를 먼저 표시한다.
원격 조회가 불가능하거나 서로 충돌하면 `UNKNOWN`을 유지한다. 네트워크 오류를 “아직 생성 안 됨”으로 해석하지 않는다.
자식 프로세스가 살아 있을 수 있는 작업자는 먼저 [운영](../operations/README.md)의 종료·lease 회수 절차를 수행한다.
`FAILED`에서 재시도하거나 `PARTIAL`에서 PR만 계속할 때도 같은 승인 범위·현재 권한을 재검사하고 관리자의 명시적 복구 입력을 기록한다.
반복 시도는 같은 commit/ref/Publication을 사용한다. 새 브랜치 이름으로 실패를 우회하지 않으며, 기존 원격 결과를 rollback·삭제하지 않는다.

승인자만 비활성화·권한 회수된 PARTIAL은 원격 읽기 대조 뒤 다른 활성 ADMIN이 `approve_remaining`으로 같은 불변 대상에 새 Approval을 남길 수 있다. 새 Approval·남은 PR Job 등록은 하나의 transaction이고 기존 승인의 행위자를 교체하지 않는다. 정책·결과·base가 바뀌었거나 원격 상태를 모르면 이 복구를 허용하지 않는다.

남은 단계를 진행할 수 없는 미완료 발행은 원격 대조·관련 프로세스 종료가 끝나고 사실에 맞는 상태가 확정된 뒤 관리자가 `남은 발행 포기`를 기록할 수 있다. `UNKNOWN`을 유지한 채 pin을 해제할 수는 없다. 포기는 기존 승인과 추가 Job 등록을 무효화하고 pin을 해제하지만 실제 관측 상태·원격 링크·포기 사유는 보존한다. 이를 성공이나 rollback으로 바꾸지 않으며 포기한 Publication을 재실행하지 않는다.

위 값은 현재 로컬 제품의 구현 결정이다. 새 사용자 결정을 기다리는 항목이 아니며, 모드 같은 운영값은 관리자가 명시적으로 변경할 수 있다.

## 12. 완료 조건과 기존 구현에서 바꿀 점

- [ ] 매니저의 직접 POST·ID 바꾸기·모델 요청이 모두 거부되고 승인·Job·Git 부작용이 없는 테스트가 있다.
- [ ] 다른 기기 여부와 무관하게 활성 관리자 계정만 같은 권한을 가지며, 로그아웃·권한 회수 후 재검사한다.
- [ ] 승인 경합·중복 제출·DB rollback에서 승인과 Job이 정확히 한 쌍으로 기록된다.
- [ ] 결과·기준 SHA·프로젝트 설정·원격 저장소 바꾸기가 기존 승인을 무효화한다.
- [ ] 필수 검증 없음·실패·미수행·불완전 결과·비밀 포함 결과는 발행할 수 없다.
- [ ] 훅·필터·변조 Git 설정 fixture를 발행 사본으로 가져오거나 실행하지 않는다.
- [ ] 동시 ref 생성에서 기존 ref를 덮어쓰지 않고, 승인된 단일 commit·새 ref만 전송한다.
- [ ] push 성공/PR 실패, push·PR 응답 유실, 작업자 재시작 후 중복 없는 복구를 각각 검증한다.
- [ ] 자격증명 접근 canary 통과와 실제 원격 발행 검증을 별도로 보고한다. 실제 원격 검증에는 허용된 저장소·행동 범위가 필요하다.
- [ ] 로컬 결과 생성 후 발행 최초 활성화만으로 Codex 재실행을 요구하지 않으며 새 정책 대상은 명시적으로 승인받는다.
- [ ] push 뒤 승인자 권한 회수 시 다른 ADMIN의 남은 단계 재승인은 같은 결과·commit·ref에만 적용되고 재push하지 않는다.
