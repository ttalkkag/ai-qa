# 로컬 프로젝트와 작업 정책

> 상태: 로컬 Django 제품의 구현 기준. 현재 `devauto` 설정을 그대로 새 계약으로 승격하지 않습니다.

## 1. 목적과 책임

관리자가 신뢰하는 로컬 Git 저장소를 등록하고, 매니저가 경로·브랜치·검증 명령을 몰라도 안전한 작업 범위를 선택하게 합니다.
이 도메인은 프로젝트 식별, 원본 저장소 위치, 기준 ref, 버전 있는 작업 정책, 관리자 등록 검증 명령, 준비 상태를 소유합니다.

### 첫 사용 안내와 등록 화면

- 등록된 프로젝트가 없는 ADMIN의 첫 화면은 본문 중앙에 짧은 설명·`프로젝트 추가` 버튼·`프로젝트 등록 가이드` 링크만 표시한다. 별도 시작 순서나 펼침 안내는 표시하지 않는다.
- 프로젝트가 있으면 목록을 표시하며 본문의 추가 버튼·등록 가이드를 제거한다. ADMIN에게만 프로젝트 목록의 네비게이션 우측에 작은 `Add` 버튼을 표시한다. 헤더·다른 페이지의 네비에는 추가하지 않는다.
- 등록된 목록은 경계가 있는 표로 프로젝트 이름·설명, 프로젝트 상태, 마지막 확인을 분리한다. 상태는 색상과 문구가 있는 배지로 표시하며 아카이브를 준비 상태보다 우선한다. 760px 이하에서는 프로젝트별 묶음으로 전환하고 상태·확인 시각에 항목명을 유지한다. 긴 이름·설명은 줄바꿈하며 상세 화면은 이름 링크로 연다. 미커밋 변경은 상태 아래 보조 정보로 표시한다.
- MANAGER에게 할당된 프로젝트가 없으면 중앙에 관리자 문의 안내·사용 가이드만 표시한다. 프로젝트가 있으면 할당된 목록을 표시한다. 추가 버튼·서버 경로·AI 설정·계정 할당 링크는 노출하지 않는다.
- 등록·작업 준비·매니저 할당·요청 시작의 상세 순서는 Docs에서 설명한다. 관리자 본인만 사용하면 매니저 할당은 생략할 수 있다. 등록은 자동 수정·커밋·원격 발행이 아니다.
- 등록 폼 도움말은 이름의 구분 용도, 선택 사항인 서비스·담당 업무 설명, 서버 PC의 Git 최상위 폴더와 준비 조건, 브랜치 미입력 시 선택 순서만 간단히 제공한다. 경로 준비 조건은 다음 줄에 괄호로 표시한다. 예시 경로는 실제 값으로 저장하거나 자동 입력하지 않는다.
- 경로 도움말과 Docs 등록 가이드는 공통 조건 다음에 `macOS: /Users/your-name/Projects/sample-board`, `Windows: C:\Users\your-name\Projects\sample-board`를 각각 한 줄로 표시한다. 복사 방법과 OS별 부연 설명은 표시하지 않는다. 경로 예시 표기는 Windows 런타임 지원을 의미하지 않으며 현재 실행 기준은 macOS이다.
- 등록 화면의 네비는 `Project / Add Project`이다. 본문 제목·상단 설명·등록 전후 안내 섹션을 두지 않고, 각 입력란 아래에 구체적인 도움말을 제공한다. Git 폴더·커밋 준비·경로 예시는 경로 입력란에서 설명한다. 동의 체크박스는 사용하지 않으며, 필수 입력·절대 경로 형식을 검증한 뒤 제출 모달에서 이름·경로·브랜치를 확인한다. 모달 제목은 `프로젝트 생성`, 설명은 `프로젝트를 등록할까요?`이며 긴 부연 설명은 표시하지 않는다. `예`만 제출하고 `아니오`·Esc는 입력을 유지한다. 서버에서 실제 저장소·기준 ref·권한을 다시 검사한다.
- 폼 맨 아래 우측에 `프로젝트 등록` 버튼을 놓고 바로 왼쪽에 `프로젝트 등록 가이드` 링크를 둔다. 등록 후 수정 범위·필수 검증·AI 준비·매니저 할당 안내는 중복하지 않고 Docs의 등록 가이드에서 제공한다.
- 목록의 준비 상태는 저장된 마지막 ProjectHealth 진단과 시각을 표시한다. AI 연결·실행 보호·모델 검증 완료나 실제 실행 성공으로 표현하지 않는다. GET 화면 조회는 새 진단·모델 호출·계정 할당을 실행하지 않는다.
- `/docs/#project-setup`의 관리자 전용 안내는 등록 예시, 후속 설정, 경로·기준 버전 오류 대응을 제공한다. MANAGER에게는 이 섹션과 목차 링크를 숨긴다.

책임을 다음과 같이 나눕니다.

## 2. 등록과 사용 흐름

1. 관리자는 `프로젝트 추가`에서 표시 이름, 로컬 저장소 절대 경로, 기준 local ref를 입력합니다.
2. 앱은 읽기 전용으로 Git 저장소·기준 commit·dirty 상태·파일 정책을 점검하고 결과를 보여줍니다.
3. 관리자는 수정 허용 경로와 검증 명령을 등록합니다. 필수 검증이 하나도 없으면 수정 실행을 허용하지 않습니다.
4. 프로젝트 사용자를 할당합니다. 멤버십 변경은 계정 도메인의 Interface를 사용합니다.
5. 매니저는 프로젝트 표시 이름과 설명, 준비 상태를 보고 선택합니다. 원본의 절대 경로와 실행 명령은 입력하지 않습니다.
6. 요청 확인 화면에서 local ref를 commit SHA로 해석해 정책 버전과 함께 표시합니다. 확정 시 표시값이 여전히 현재값과 같은지 검사하고 그 값을 고정합니다.
7. 수정 시작 시 해당 SHA와 정책을 재검사하고, 원본과 분리된 작업 사본을 준비합니다.

등록·점검은 저장소를 수정하거나 검증 명령을 실행하지 않습니다. 검증 명령의 실제 실행은 별도 실행 기록으로 남깁니다.
앱 저장소에 `docs/`나 `.ai-context`가 있어야 한다는 조건은 두지 않습니다. 대상 프로젝트의 프레임워크도 제한하지 않습니다.

## 3. 화면과 필수 입력

프로젝트 상세는 상단의 상태 요약과 새로고침, 브랜치·기준 코드·마지막 확인·미커밋 변경 요약을 먼저 표시한다. 상태는 저장된 진단을 기준으로 `프로젝트 준비 완료 / 프로젝트 설정 필요 / 저장소 접근 불가 / 상태 확인 필요`를 구분하고 아카이브 상태를 우선한다. 마지막 확인 시각을 함께 표시하며 조회만으로 재진단하거나 AI를 실행하지 않는다. 프로젝트 준비 완료는 AI 실행 준비나 실제 검사 통과를 의미하지 않는다.

본문은 필요한 조치를 한 번만 안내하고 작업 범위·AI 별도 확인·등록 검증 수와 필수 여부를 보여준다. `.`은 `프로젝트 전체`로 표시한다. 실제 검사 결과는 각 요청의 실행 결과에서 확인한다. 관리자는 우측 관리 영역에서 경로·설정 링크를 확인하고 상태 변경 폼은 필요할 때 펼친다. 모바일은 관리 영역을 본문 아래에 배치한다. 매니저에게는 관리 영역·원본 경로·관리자 전용 링크를 표시하지 않는다. 큰 페이지 제목과 중복 안내는 추가하지 않는다.

헤더의 `Project`(`/projects/`)가 목록 진입점이며 로고와 로그인 후 메인 진입도 이 목록으로 연결합니다. 프로젝트 상세·설정·대화·프로젝트별 발행 설정은 `Project`를 활성 메뉴로 유지합니다. 네비게이션은 `Project / 프로젝트 이름 / 작업 정책 설정`처럼 표시하며, 목록·프로젝트 이름을 누르면 해당 화면으로 이동합니다. 운영자 전체 승인 목록은 별도의 `Admin` 하위이며 프로젝트별 발행 설정과 혼동하지 않습니다. 전체 경로 규칙은 [내비게이션](../navigation/README.md)을 따릅니다.

| 화면 | 관리자 입력 | 매니저에게 보이는 내용 |
| --- | --- | --- |
| 프로젝트 목록 | 새 프로젝트 추가 | 할당된 프로젝트의 이름·설명·준비 상태 |
| 기본 설정 | 이름, 설명 선택, 로컬 경로, 기준 ref | 이름·설명, 기준 버전의 짧은 SHA |
| 작업 정책 | 읽기·수정 허용 경로, 제외 경로 | 허용 작업 범위와 실행 불가 이유의 쉬운 설명 |
| 검증 설정 | 이름, TEST/COMMAND 종류, TEST parser, argv, 상대 cwd, timeout, required | 검증 이름, 필수 여부, 마지막 실제 결과 |
| 프로젝트 진단 | 읽기 전용 재점검 버튼 | `준비됨` 또는 해결할 설정 항목 |
| 운영 설정 | 활성/아카이브, 사용자 할당, 발행 설정 링크 | 아카이브 표시와 과거 요청 조회 |

매니저의 요청 폼에는 Git URL·임의 branch·로컬 경로·shell command·환경변수·API 키 입력란을 만들지 않습니다.
발행 설정 화면과 `발행 활성화` 표시의 원본 데이터는 승인 도메인이 소유합니다. 프로젝트 화면은 그 상태를 참조합니다.
프로젝트가 없을 때 관리자는 `프로젝트를 연결하고 시작하세요.`, 매니저는 `할당된 프로젝트가 없습니다. 관리자에게 문의하세요.`를 봅니다. 최초 관리자 안내는 요청 작성이 아닌, 프로젝트를 연결해 매니저의 요청을 받을 준비를 하는 목적입니다. 사용 방법은 가이드 링크나 헤더의 문서 아이콘 `Docs`에서 확인합니다.

## 4. 핵심 데이터

| 데이터 | 필수 값과 규칙 |
| --- | --- |
| `Project` | 불변 ID, name, description, canonical_repo_path, state, project_config_version, publication_policy_id 선택, created_by, timestamps |
| `ProjectConfigRevision` | project_id, project_config_version, source_ref, read_paths, write_paths, excluded_paths, created_by, created_at; 변경 불가 이력 |
| `VerificationCommand` | config_revision, command_id, display_name, kind(TEST/COMMAND), parser_id·version(TEST 필수), report_path(JUnit 필수), argv 배열, cwd 상대 경로, timeout_sec, required, generated_paths, 순서 |
| `PreparationCommand` | config_revision, command_id, argv 배열, cwd 상대 경로, timeout_sec, dependency_bundle_id 선택; Docker 안의 환경 준비 |
| `DependencyBundle` | project_id, lock_file_hash, platform·runtime, manifest_sha256, 관리자 등록 경로, created_by; 내용 고정·실행 중 변경 불가 |
| `ProjectHealth` | 확인 시간, 실제 repo 경로, 해석된 SHA, dirty 여부·수량, readiness, blocking_reasons; 진단 결과이지 영구 권한 아님 |

프로젝트 입력 항목은 `Name*:`, `Description:`, `Path*:`, `Branch:`로 표시합니다. 이름·경로만 필수 입력으로 별표를 표시합니다. Branch는 선택 입력이며 미입력 시 자동 선택 동작을 유지합니다.

`source_ref`는 로컬 브랜치명입니다. 등록·작업 정책 설정 화면은 `Branch`로 표시하며 플레이스홀더는 사용하지 않습니다. 커밋 SHA·임의 Git revision expression·shell fragment는 입력받지 않습니다. 실행 시 선택 브랜치를 해석한 `base_commit_sha`와 기존 실행 이력의 SHA 고정은 유지합니다.

직접 입력하는 브랜치는 공통 base hook의 명명 규칙을 따릅니다. `main`, `master`, `develop`, `staging` 또는 소문자 `type/description` 형식이며 여러 단계의 경로를 허용합니다. type은 영문 소문자, 각 하위 구간의 첫 글자는 영문 소문자·숫자, 이후 문자는 영문 소문자·숫자·점·밑줄·하이픈입니다. 예: `temp/ai-qa-testing`, `fix/api/login`. Git 자체의 금지 문법도 별도로 검사합니다. 기존 `refs/heads/` 표기 호환은 유지합니다.

브라우저 입력 검증은 확인 모달 전에 동작하고, 서버 폼 및 등록·설정 저장 서비스가 다시 검사합니다. 대상 저장소의 hook 파일을 읽거나 실행해 규칙을 자동 수집하지 않으며, 이 검증이 commit-msg/pre-push hook 설치나 실행을 대신하지 않습니다. 기존 저장된 기준의 조회·실행 및 빈 입력의 현재 브랜치 자동 선택에는 Git 문법 검사를 유지하여 기존 이력을 변경하지 않습니다.
발행 대상의 base branch와 소스 `source_ref`는 다른 값입니다. 원격 저장소·대상 branch·발행 모드의 정의는 [승인과 발행](../approvals/README.md)을 따릅니다.
프로젝트 이름·설명 수정은 실행 정책을 바꾸지 않습니다. 소스 위치·ref·파일 범위·검증 명령을 바꾸면 새 설정 버전을 만듭니다.
준비 명령·의존성 묶음 변경도 실행 설정 버전을 증가시킵니다. 발행 활성화·대상·모드는 별도 `PublicationPolicy.version`만 증가시킵니다. 발행 설정 변경은 과거 발행 승인을 무효화하지만 코드와 검증이 같은 로컬 결과를 무효화하거나 Codex 재실행을 요구하지 않습니다.
실행은 설정 row를 다시 참조해 최신값으로 덮어쓰지 않고, 확정된 revision을 보존합니다.

## 5. 원본 저장소와 기준 버전 규칙

- 관리자만 프로젝트를 등록합니다. 임의 URL clone 대신 호스트에 존재하는 신뢰한 로컬 Git 저장소를 사용합니다.
- 실제 경로를 정규화해 저장하고 Git 최상위 경로가 입력한 프로젝트 root와 일치하는지 확인합니다.
- `/`, 사용자 홈 전체, 앱 런타임 데이터 root를 프로젝트로 등록하지 않습니다. 원본과 앱 작업 사본 경로가 중첩되지 않아야 합니다.
- 아직 commit이 없는 저장소나 읽을 수 없는 Git 객체는 AI 소스 작업을 차단합니다. 이미 저장한 기준 브랜치가 나중에 삭제된 경우도 읽기 점검·실행에서는 자동 복구하지 않고 `준비 필요`로 표시합니다.
- 등록·작업 정책 저장 시 기준 브랜치를 비워 두면 존재하는 로컬 브랜치를 `develop → main → master → 현재 브랜치` 순서로 선택해 저장합니다. 원격 추적 브랜치와 태그는 후보가 아닙니다. 직접 입력한 브랜치가 있으면 그대로 사용하고, 없으면 같은 우선순위로 선택한 시작 커밋에서 **입력한 이름의 로컬 브랜치를 생성**합니다. 이름·정책·권한·설정 버전을 검증한 후 생성하며 기존 ref를 덮어쓰지 않습니다. 브랜치 이름의 경로 충돌이나 권한 오류는 저장 실패로 안내합니다. 원본 checkout·파일 변경·자동 커밋·원격 push는 하지 않습니다. Git ref 생성과 DB 저장은 하나의 원자적 트랜잭션이 아니므로 후속 DB 오류 시 생성된 브랜치가 남을 수 있으며, 재시도는 기존 브랜치를 재사용합니다.
- detached HEAD에서도 앞의 세 후보 중 존재하는 브랜치를 시작점으로 사용합니다. 모두 없으면 기존 커밋이 있는 브랜치를 직접 지정하거나 서버에서 먼저 준비해야 합니다. 기존 설정에 SHA가 저장되어 있다면 자동 변환하지 않으며 관리자가 브랜치로 새 설정 버전을 저장해야 합니다.
- dirty·staged·untracked 파일은 그대로 보존하고 **실행 입력에서 제외**합니다. commit된 기준 SHA만 실행 입력이 됩니다.
- 매니저에게도 `현재 저장하지 않은 Git 변경 N건은 이번 작업에 포함되지 않습니다`를 표시합니다. 파일 내용·비밀정보를 경고에 노출하지 않습니다.
- dirty 상태를 해결한다며 앱이 stash·reset·clean·commit·checkout하지 않습니다. 최신 원격 변경을 얻기 위해 자동 fetch/pull하지도 않습니다.
- 명세 확정 뒤 ref가 다른 SHA로 이동하면 바로 실행하지 않습니다. 요청 도메인에 기준 변경을 알리고 새 버전을 확인하게 합니다.
- queued 실행은 claim 직전 확정 SHA·정책을 검사합니다. 실행 중 ref 이동으로 이미 준비된 snapshot의 기준을 바꾸지 않습니다.
- 실제 snapshot 방식, Git 메타데이터와 symlink·submodule·LFS 처리, 원본 무변경 검증은 실행 도메인이 소유합니다.

원본 dirty가 있다는 이유만으로 유효한 committed SHA의 실행을 막지는 않습니다. 그러나 최신 미커밋 화면을 고칠 것으로 오인하게 해서는 안 됩니다.

## 6. 파일 범위와 검증 명령

파일 경로 정책은 프로젝트 root 기준 상대 경로 목록입니다. 경로 탈출, 절대 경로, 제어 문자, symlink를 통한 탈출은 허용하지 않습니다.
읽기 허용 범위와 수정 허용 범위를 구분합니다. 제외 규칙이 허용 규칙보다 우선하며 결과 변경 검증에도 같은 정책을 적용합니다.
수정 허용 범위는 읽기 허용 범위의 부분집합이어야 합니다. 컨테이너에는 허용된 프로젝트 사본을 제공하며 결과 수집 시 수정 허용 범위 밖의 변경은 거부합니다. 경로별 OS 쓰기 차단을 보장한다는 뜻은 아닙니다.
읽기·수정 허용 범위의 초기값은 `.`이며, 등록 화면에서 관리자가 확인해야 합니다. 제한된 하위 디렉터리로 좁힐 수 있습니다.
초기 제외 기본값에는 `.env`, `.env.*`, 인증 키·토큰 파일, `.git/`, 로컬 데이터·의존성·빌드 결과 디렉터리를 포함합니다.
이는 AI에 제공할 원본 소스와 결과 diff의 범위입니다. 사본 안에 새로 만든 `.venv`·도구 캐시는 준비/검사 실행에 필요한 읽기·실행만 별도 허용하며 원본의 동명 디렉터리는 읽거나 공유하지 않습니다. `.aiqa-inputs/`와 `.aiqa-output/`은 앱 예약 경로이므로 기준 tree에 이미 있으면 등록을 거부합니다. 검증에 필요한 source가 읽기 범위 밖이면 정책을 우회하지 않고 준비 실패로 안내합니다.
대상 프로젝트에 필요한 예외는 관리자 정책으로만 등록하며, 프로세스 자체의 인증정보 접근 금지까지 해제하는 예외는 제공하지 않습니다.

검증 명령은 다음 형태의 **구조화된 관리자 입력**입니다. 아래 값은 형식 예이며 이 프로젝트에서 실행한 결과가 아닙니다.

```json
{
  "command_id": "unit",
  "display_name": "단위 테스트",
  "kind": "TEST",
  "parser_id": "pytest-summary",
  "parser_version": 1,
  "argv": [".venv/bin/python", "-m", "pytest", "-q"],
  "cwd": ".",
  "timeout_sec": 300,
  "required": true
}
```

- argv는 비어 있지 않은 문자열 배열이며 shell을 사용하지 않습니다. 매니저 텍스트를 명령으로 이어 붙이지 않습니다.
- executable은 관리자가 허용한 호스트 도구 경로나 작업 사본 안의 실행 파일로 해석합니다. cwd는 실행 사본 안의 존재하는 디렉터리여야 합니다.
- `sh -c`, `bash -c` 등 raw shell wrapper, inline secret, 요청 텍스트 치환, 원본 저장소를 쓰기 대상으로 삼는 인자는 등록을 거부합니다.
- timeout은 명령별 양의 정수이며 기본 300초, 최대 1,800초입니다. 앱 전체 실행 시간 제한은 실행 도메인을 따릅니다.
- 필수 명령이 최소 하나 있어야 수정 실행이 가능합니다. 등록만 했거나 미실행인 명령은 통과가 아닙니다.
- TEST에는 지원 parser를 반드시 지정합니다. 초기 지원은 pytest summary와 JUnit XML이며, 그 밖의 프레임워크는 JUnit 결과를 생성하거나 parser를 구현·검증한 뒤 활성화합니다. lint/build는 COMMAND와 parser 없음으로 등록합니다.
- JUnit의 `report_path`는 `.aiqa-output/<command_id>/junit.xml` 같은 사본 기준 상대 경로로 고정하고 명령 argv의 출력 위치와 일치시킵니다. BASELINE/AFTER와 각 검사에는 비어 있는 전용 출력 경로를 새로 준비합니다. 기존 보고서를 glob으로 찾아 쓰지 않으며 해당 실행이 만든 정상 XML이 없으면 UNVERIFIED입니다.
- `generated_paths`는 테스트 cache·build 출력 등 준비/검사가 쓸 상대 경로 목록입니다. 초기값은 `.aiqa-output/`이며 필요 경로만 관리자가 추가합니다. 어떤 committed 파일/후보 source도 이 경로 아래 있으면 거부하여 생성물 제외 규칙으로 코드 변경을 숨기지 못하게 합니다. 검사 source는 읽기 전용이고 자동 bytecode 생성은 끄거나 전용 출력 경로로 보냅니다.
- skipped 항목 자체는 통과 수에 넣지 않습니다. 실제 실행 0개·전부 skip·수집/해석 불명은 통과로 집계하지 않습니다. 일부 skip이 있더라도 실행된 테스트가 1개 이상이고 실패 0·증거 완전이면 PASS와 skip 수를 함께 표시합니다. lint/build의 테스트 수는 해당 없음으로 표시합니다.
- 명령이 참조하는 저장소 스크립트도 코드를 실행합니다. 관리자 등록이나 `shell=False`만으로 안전해지지 않으므로 AI/실행 도메인의 실행 통제를 동일하게 적용합니다.
- 의존성이 부족하면 `DEPENDENCY_MISSING`으로 중단하고 관리자에게 필요한 조치를 표시합니다. 검증 전에 패키지를 자동 설치하지 않습니다.
- 관리자는 같은 argv·cwd·timeout 제약을 가진 준비 명령과 hash로 고정한 의존성 묶음을 선택적으로 등록합니다. 등록된 준비는 해당 설정 버전의 각 사본에서 반복 실행할 수 있으며, 관리자 확인 없이 명령·묶음을 바꾸지 않습니다. 준비 성공은 검증 통과를 대신하지 않습니다.
- 준비·모델 도구·검사는 Docker 컨테이너 안에서 네트워크를 사용할 수 있습니다. 원본 저장소에 설치하거나 원본 가상환경을 공유하지 않습니다. 선택적 오프라인 자료는 Docker 이미지의 Linux 플랫폼·Python 버전과 맞아야 합니다. [운영](../operations/README.md)의 온라인 준비 예시를 기본으로 사용합니다.

## 7. 서버 Interface와 준비 상태

| 작업 | 입력 | 결과와 주요 오류 |
| --- | --- | --- |
| `register_project` | admin, name, local_path, source_ref | 프로젝트; `INVALID_REPOSITORY`, `PATH_NOT_ALLOWED`, `BASE_REF_NOT_FOUND` |
| `update_configuration` | admin, project_id, expected_version, 구조화된 정책 | 새 revision; `VERSION_CONFLICT`, `INVALID_COMMAND`, `PROJECT_BUSY` |
| `inspect_project` | 권한 있는 actor, project_id | 읽기 전용 진단; `REPOSITORY_UNAVAILABLE`, `BASE_REF_NOT_FOUND` |
| `resolve_execution_input` | actor, project_id, expected_version, expected_sha 선택 | SHA·정책 snapshot; `PROJECT_NOT_READY`, `BASE_CHANGED`, `VERSION_CONFLICT` |
| `set_project_state` | admin, project_id, state, reason | 활성/아카이브; `PROJECT_BUSY`, `ACCESS_DENIED` |

프로젝트 영속 상태는 `ACTIVE`/`ARCHIVED` 두 가지입니다. `READY`/`SETUP_REQUIRED`/`UNAVAILABLE`는 마지막 진단과 현재 조건으로 계산하는 준비 상태입니다.
준비됨은 필요한 설정을 갖췄다는 뜻이며, 실제 수정·검증 성공을 의미하지 않습니다.
읽기 기반 대화 가능 여부와 수정 실행 가능 여부를 별도로 계산합니다. 검증 명령 미등록은 수정만 막고 설정 설명·상태 조회까지 막지 않습니다.
아카이브는 새 대화·메시지·실행을 차단하되, 권한이 있는 과거 요청·결과 조회는 유지합니다. 물리 삭제는 제공하지 않습니다.
진행 중인 해당 프로젝트의 대화 소스 읽기·수정·검증·발행 준비/실행이 있으면 실행 정책 변경과 아카이브를 `PROJECT_BUSY`로 거부합니다. 취소·프로세스 종료 확인 후 다시 변경합니다. 대기 작업은 이전 버전을 유지하며 claim 때 stale 정책·아카이브를 재검사합니다. 발행 정책 변경 중 실행 충돌 규칙은 approvals가 소유합니다.
대기 요청의 이전 정책 버전은 자동 갱신하지 않습니다. 새 정책과 기준으로 요청을 다시 확인해야 합니다.

## 9. 인수조건

- [ ] PRJ-AC-01: 관리자가 정상 로컬 Git root를 등록하고, 매니저는 이름만 선택해 요청을 시작한다.
- [ ] PRJ-AC-02: 매니저의 경로·ref·command·정책 변조는 거부되며 설정과 파일에 부작용이 없다.
- [ ] PRJ-AC-03: commit 없는 저장소·사라진 ref·금지 경로·경로 중첩이 준비 실패로 구분된다.
- [ ] PRJ-AC-04: dirty·staged·untracked를 가진 원본의 파일·index·ref가 유지되고 실행에는 지정 SHA만 반영된다.
- [ ] PRJ-AC-05: ref 또는 설정 버전 변경 후 이전 명세의 실행이 차단되고 사용자에게 재확인 이유를 표시한다.
- [ ] PRJ-AC-06: 필수 검증이 없으면 수정 실행을 막고, 미실행·실행 실패·통과를 구분한다.
- [ ] PRJ-AC-07: argv·cwd·timeout 위반과 원본 쓰기 명령을 거부하고 실제 검사도 실행 통제 안에서 수행된다.
- [ ] PRJ-AC-08: 아카이브·정책 변경의 실행 중 충돌을 거부하고, 과거 기록의 권한 있는 조회는 유지한다.

현재 `devauto/core/models.py`의 YAML·shell-string command 및 `devauto/runner/workspace.py`의 clone·checkout 흐름은 비교 자료입니다.
새 Django의 로컬 경로·불변 SHA·구조화된 명령·계정 권한 계약을 충족하는지는 별도로 구현·검증해야 합니다.
